# 스왑체인과 플립 모델

> 상태: 진행중 · 갱신 2026-08-11 · 관련: [1단계 작업일지](../작업일지/2026-08-11_1단계_창과_D3D11_초기화.md)
> 무엇: 백버퍼가 화면에 도달하는 경로 두 가지(BitBlt / Flip)의 차이와, 플립 모델을 고르면 코드에 어떤 제약이 따라오는지.

---

## 스왑체인이 무엇인가

화면에 보이는 이미지 한 장을 그리는 도중이면 찢어진 그림이 보인다.
그래서 **보이지 않는 곳에 한 장을 다 그린 다음 통째로 바꿔치기**한다.
보이는 쪽이 프런트 버퍼, 그리는 쪽이 백버퍼, 이 버퍼 묶음과 교체 규칙이 스왑체인이다.

`Present()`가 그 "바꿔치기"를 요청하는 함수다.

---

## BitBlt 모델과 플립 모델

| | BitBlt (`DXGI_SWAP_EFFECT_DISCARD`) | Flip (`DXGI_SWAP_EFFECT_FLIP_DISCARD`) |
|---|---|---|
| Present 때 하는 일 | 백버퍼를 화면 버퍼로 **복사** | 포인터를 **바꿔 끼움** |
| 대역폭 | 매 프레임 화면 크기만큼 복사 | 복사 없음 |
| 필요한 버퍼 수 | 1개 이상 | **2개 이상** |
| MSAA | 스왑체인에 직접 가능 | **불가** (`SampleDesc.Count`는 1이어야 함) |
| 등장 | DX9 시절부터 | Windows 8 / DXGI 1.2부터 |

플립 모델이 나온 이유는 **데스크톱 합성기(DWM)** 때문이다.
Windows Vista 이후 모든 창은 DWM이 한 번 더 합성해서 화면에 올린다.
BitBlt 모델은 게임이 복사하고 DWM이 또 복사했다. 플립 모델은 그 중간 복사를 없앤다.

**전체화면이 아니어도 이득이 있다는 점이 중요하다.** 창 모드가 기본인 요즘 게임에서
플립 모델이 사실상 표준인 이유다.

---

## 플립 모델을 고르면 따라오는 제약

### 1. MSAA를 스왑체인에 직접 걸 수 없다

`SampleDesc.Count`가 반드시 1이어야 한다.
안티에일리어싱이 필요하면 **멀티샘플 텍스처에 그린 뒤 `ResolveSubresource`로 백버퍼에 내리는**
방식을 직접 짜야 한다. 이 프로젝트는 2D 스프라이트라 당장은 필요 없다.

### 2. Present 뒤에 렌더 타깃 바인딩이 풀린다

이게 실수하기 쉬운 지점이다. 첫 프레임은 잘 나오는데 두 번째부터 아무것도 안 그려진다면
대개 이것이다.

> **단, `Clear`로는 이 증상을 확인할 수 없다.** `ClearRenderTargetView`는 지울 뷰를
> 인자로 직접 받으므로 파이프라인 바인딩과 무관하게 동작한다. 바인딩이 풀린 것이
> 드러나는 건 `Draw` 계열뿐이다 — 드로우 콜은 인자에 대상이 없고 미리 세팅해둔
> 상태만 읽기 때문이다. 자세한 것은
> → [기초 — Clear는 되는데 Draw는 안 되는 이유](00_기초_창과_D3D11의_등장인물.md)

```cpp
void Renderer::Render()
{
    // 매 프레임 다시 바인딩해야 한다
    ID3D11RenderTargetView* views[] = { m_backBufferView.Get() };
    m_context->OMSetRenderTargets(1, views, nullptr);

    m_context->ClearRenderTargetView(m_backBufferView.Get(), color);
    // ... 드로우 ...
    m_swapChain->Present(1, 0);   // 여기서 바인딩이 풀린다
}
```

플립 모델은 Present 시점에 백버퍼의 소유권을 DWM에 넘긴다.
넘어간 리소스를 파이프라인이 계속 붙들고 있으면 안 되므로 런타임이 바인딩을 끊는다.

### 3. 초기화 경로가 길어진다

`D3D11CreateDeviceAndSwapChain`은 BitBlt 모델만 만든다.
플립 모델은 `IDXGIFactory2::CreateSwapChainForHwnd`로만 만들 수 있고,
그러려면 디바이스를 만든 어댑터의 팩토리를 손에 넣어야 한다.

```
ID3D11Device --As()--> IDXGIDevice --GetAdapter()--> IDXGIAdapter --GetParent()--> IDXGIFactory2
```

**왜 아무 팩토리나 쓰면 안 되는가**: 멀티 GPU 환경에서 디바이스가 만들어진 어댑터와
다른 어댑터의 팩토리로 스왑체인을 만들면 어긋난다. 디바이스에서 거슬러 올라가면
정의상 같은 어댑터가 나온다.

## ResizeBuffers 규칙

창 크기가 바뀌면 백버퍼도 다시 잡아야 한다. `ResizeBuffers`는
**그 버퍼를 참조하는 것이 전부 사라진 뒤에만** 성공한다.

```cpp
m_backBufferView.Reset();                            // 1. 뷰 해제
m_context->OMSetRenderTargets(0, nullptr, nullptr);  // 2. 파이프라인 바인딩 해제
m_context->Flush();                                  // 3. 지연 참조 정리
m_swapChain->ResizeBuffers(0, w, h, DXGI_FORMAT_UNKNOWN, 0);
```

2번을 빠뜨리면 `DXGI_ERROR_INVALID_CALL`이 난다. 뷰를 놓아도 디바이스 컨텍스트가
아직 붙들고 있기 때문이다.

인자에 0과 `DXGI_FORMAT_UNKNOWN`을 넘기면 각각 "현재 값을 유지"라는 뜻이다.
버퍼 개수와 포맷을 다시 적지 않아도 된다.

## Present의 SyncInterval — 성능을 잴 때 반드시 건드릴 곳

```cpp
m_swapChain->Present(1, 0);   // 수직동기 대기
m_swapChain->Present(0, 0);   // 즉시
```

| 값 | 동작 | 언제 |
|---|---|---|
| 1 | 다음 수직동기까지 기다림. 찢김 없음 | 평소 보기 |
| 0 | 기다리지 않음. 찢길 수 있음 | **성능 측정** |

**`1`로 둔 채 성능을 재면 안 된다.** 프레임 시간이 모니터 주사율에 고정되므로
스프라이트를 100개 그리든 10000개 그리든 똑같이 144 FPS가 나온다.
GPU가 놀고 있는 시간이 전부 대기로 흡수되어 차이가 통째로 사라진다.

4단계에서 개별 드로우 콜과 배칭을 비교할 때 이걸 잊으면 **"차이가 없다"는 잘못된 결론**을
얻게 된다. MiniOscReceiver에서 저부하로 재고 "세 방식이 똑같다"고 착각했던 것과 같은 종류의 실수다.
