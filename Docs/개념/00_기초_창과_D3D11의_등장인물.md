# 00. 기초 — 창과 D3D11의 등장인물

> 상태: 진행중 · 갱신 2026-08-11 · 관련: [작업일지 목차](../_목차.md), [1단계 작업일지](../작업일지/2026-08-11_1단계_창과_D3D11_초기화.md), [스왑체인과 플립 모델](스왑체인과_플립모델.md)
> 무엇: DirectX를 처음 보는 상태에서 1단계 코드를 읽기 위해 필요한 최소한의 그림. 창은 왜 필요하고, D3D11의 주요 객체 넷은 각각 무슨 일을 하는가.

---

## 큰 그림 — 세계가 둘이다

```
[ Windows 세계 ]                      [ Direct3D 세계 ]
 창을 만들고 관리한다        ←HWND→     그 창 안에 그림을 그린다
 마우스·키보드·창 크기                  GPU에게 명령한다
```

**Windows는 창까지만 책임진다.** 창 안을 뭘로 채울지는 관심이 없다.
그래서 할 일이 두 단계다 — ① 창을 하나 만들고 ② "이 창 안쪽은 내가 그린다"고 D3D에 등록한다.

둘을 잇는 것이 `HWND`다. **창의 번호표**다.
실제 창 데이터는 Windows가 갖고 있고, 우리는 번호만 받아서 "몇 번 창에 그려줘"라고 말한다.

---

## 1부. 창 만들기 (`Window.cpp`)

### 왜 "클래스 등록"부터 하는가

```cpp
WNDCLASSEXW wc{};
wc.lpfnWndProc = &Window::WndProcStatic;
RegisterClassExW(&wc);
```

창을 달라고 하기 전에 **"내가 만들 창은 이런 종류다"를 먼저 신고**해야 한다.
붕어빵 틀을 등록하고 그 틀로 붕어빵을 찍는 것과 같다. 틀 하나로 창을 여러 개 만들 수 있다.

제일 중요한 필드가 `lpfnWndProc`다. **Windows가 우리한테 말을 걸 때 쓸 전화번호.**

### 메시지 — Windows가 말을 거는 방식

Windows는 프로그램에 계속 편지를 보낸다.

| 메시지 | 뜻 |
|---|---|
| `WM_MOUSEMOVE` | 마우스가 움직였다 |
| `WM_SIZE` | 창 크기가 바뀌었다 |
| `WM_CLOSE` | 닫기 버튼이 눌렸다 |
| `WM_KEYDOWN` | 키가 눌렸다 |
| `WM_DESTROY` | 창이 없어졌다 |

이 편지들이 **우체통(메시지 큐)**에 쌓인다. 우리가 할 일은 우체통을 계속 확인하는 것.

```cpp
while (PeekMessageW(&msg, nullptr, 0, 0, PM_REMOVE))  // 우체통에서 하나 꺼내
{
    DispatchMessageW(&msg);   // 아까 등록한 전화번호(WndProc)로 배달
}
```

그러면 `WndProc`이 불려서 "아, 창 크기가 바뀌었구나" 하고 처리한다.

### `PeekMessage`와 `GetMessage`

| | 동작 | 맞는 프로그램 |
|---|---|---|
| `GetMessage` | 편지가 올 때까지 **기다린다** | 메모장 — 입력이 없으면 화면도 안 변한다 |
| `PeekMessage` | 우체통이 비면 **그냥 지나간다** | 게임 — 입력이 없어도 계속 그려야 한다 |

`GetMessage`로 짜면 마우스를 안 움직이는 동안 화면이 멈춘다.

### 게임 루프

그래서 `main.cpp`가 이렇게 생겼다.

```cpp
while (window.PumpMessages())   // 편지 다 처리하고, 창 살아있으면 true
{
    renderer.Render();          // 한 프레임 그린다
}
```

**이것이 게임의 심장이다.** 초당 60번, 144번 이 루프가 돈다.

## 2부. Direct3D의 등장인물 넷

### ① Device — 만드는 사람

```cpp
m_device->CreateRenderTargetView(...)
```

**뭔가를 새로 만들 때만** 쓴다. 버퍼, 텍스처, 셰이더 전부 Device가 만든다.

### ② DeviceContext — 시키는 사람

```cpp
m_context->ClearRenderTargetView(...)
m_context->OMSetRenderTargets(...)
```

**만들어진 것을 가지고 실제로 그리라고 명령**한다.

> **규칙 하나만 외우면 된다**
> `CreateOOO` → 전부 **Device**
> `OOSetOOO`, `ClearOOO`, `DrawOOO` → 전부 **Context**
>
> D3D11 함수 대부분이 이 둘 중 하나다. 헷갈리면 "만드는 거야, 시키는 거야?"만 물어본다.

### ③ SwapChain — 그림 두 장

그리는 중인 것을 그대로 보여주면 반쯤 그려진 화면이 보인다. 그래서 종이를 두 장 쓴다.

```
앞장(프런트) : 지금 화면에 보이는 것
뒷장(백)     : 우리가 지금 그리고 있는 것

다 그렸으면 → Present() → 뒤집는다
```

`Present()`가 그 "뒤집기"다. 그래서 스왑(swap)체인이다.
자세한 것은 → [스왑체인과 플립 모델](스왑체인과_플립모델.md)

### ④ RenderTargetView — 용도 꼬리표

처음에 제일 안 와닿는 부분.

백버퍼는 그냥 **텍스처 한 장**(`ID3D11Texture2D`)이다. 그런데 텍스처는 두 가지로 쓸 수 있다.

- **그리는 대상**으로 (여기에 칠한다) → `RenderTargetView`
- **읽는 재료**로 (이 그림을 붙인다) → `ShaderResourceView`

같은 텍스처인데 용도가 다르다. 그래서 텍스처를 직접 넘기지 않고,
**"이 텍스처를 이 용도로 쓴다"는 꼬리표**를 만들어 넘긴다. 그것이 뷰(View)다.

```cpp
swapChain->GetBuffer(0, ...)             // 백버퍼 텍스처를 꺼내고
device->CreateRenderTargetView(...)      // "여기에 그린다" 꼬리표를 만든다
```

## 3부. 매 프레임 무슨 일이 일어나나

`Renderer::Render()` 전체가 세 줄이다.

```cpp
m_context->OMSetRenderTargets(1, views, nullptr);     // ① 어디에 그릴지 지정
m_context->ClearRenderTargetView(view, kClearColor);  // ② 싹 지우기
m_swapChain->Present(1, 0);                           // ③ 화면에 넘기기
```

① **어디에 그릴지 지정** — 도화지를 이젤에 올린다.
② **싹 지우기** — 지난 프레임 그림이 남아 있으니 한 색으로 덮는다.
③ **넘기기** — 뒤집는다.

**②와 ③ 사이가 앞으로 코드가 들어갈 자리다.** 2단계에서 삼각형, 3단계에서 스프라이트가 여기 들어간다.

---

## 중요 — `Clear`는 되는데 `Draw`는 안 되는 이유

> 2026-08-11 확인. 처음에 "`OMSetRenderTargets`를 주석 처리하면 첫 프레임만 나올 것"이라고
> 예상했는데 **틀렸다.** 멀쩡히 계속 나온다. 왜 그런지가 D3D11의 핵심 설계를 짚는다.

`ClearRenderTargetView`는 **지울 대상을 인자로 직접 받는다.**

```cpp
m_context->ClearRenderTargetView(m_backBufferView.Get(), color);
//                               ↑ 뷰가 직접 들어감
```

"저 도화지를 이 색으로 칠해줘"라고 **손가락으로 가리키는** 것이다.
파이프라인에 무엇이 묶여 있든 상관없다.

`Draw` 계열은 완전히 다르다.

```cpp
m_context->DrawIndexed(indexCount, startIndex, baseVertex);
```

**어디에 그릴지, 무엇을 그릴지, 어떤 셰이더로 그릴지가 하나도 안 적혀 있다.** 개수만 있다.
나머지는 전부 **미리 `Set`해둔 것**에서 온다.

| 종류 | 방식 | 예 |
|---|---|---|
| **직접 지정형** | 대상을 인자로 받음. 파이프라인 무관 | `ClearRenderTargetView`, `Map`, `CopyResource`, `UpdateSubresource` |
| **상태 의존형** | 미리 묶어둔 것만 보고 동작 | `Draw`, `DrawIndexed`, `DrawInstanced` |

비유하면 —

- `Clear`는 **"저 도화지 빨갛게 칠해"** — 도화지를 가리킨다.
- `Draw`는 그냥 **"그려"** — 이젤에 뭐가 올려져 있고, 붓에 뭐가 묻었고, 물감이 뭔지를
  미리 다 세팅해둔 상태에서 던지는 한마디다.

`OMSetRenderTargets`는 "이젤에 도화지 올리기"다. **그림을 안 그리면 올려두든 말든 티가 안 난다.**

그래서 이 실험은 2단계로 미룬다. 삼각형이 생긴 뒤에 주석 처리하면 진짜로 안 나온다.
`Present` 뒤에 바인딩이 풀린다는 것의 의미도 그때 눈에 보인다.

> **면접에서 쓸 수 있는 형태** — D3D11은 상태 기반(state-based) API다.
> 드로우 콜은 인자에 대상을 담지 않고, 그 전에 세팅해둔 파이프라인 상태를 읽어 동작한다.
> 반면 Clear/Map/Copy 같은 리소스 조작은 대상을 명시적으로 받으므로 상태와 무관하다.

## 코드 지도

| 파일 · 함수 | 하는 일 | 위 설명의 |
|---|---|---|
| `Window::Create()` | 붕어빵 틀 등록 + 창 생성 | 1부 |
| `Window::WndProc()` | Windows 편지 처리 | 1부 |
| `Window::PumpMessages()` | 우체통 확인 | 1부 |
| `Renderer::CreateDeviceAndSwapChain()` | 등장인물 ①②③ 만들기 | 2부 |
| `Renderer::CreateBackBufferView()` | 등장인물 ④ 만들기 | 2부 |
| `Renderer::Render()` | 지우고 넘기기 | 3부 |
| `main.cpp` | 둘을 잇고 루프 돌리기 | 1부 |

`Common.h`(에러 검사)와 `FrameTimer.h`(시간 재기)는 곁다리라 지금은 몰라도 된다.

## 직접 만져보기

읽는 것보다 바꿔보는 것이 열 배 빠르다.

**1. 색 바꾸기** — `Renderer.cpp` 위쪽

```cpp
constexpr float kClearColor[4] = { 0.09f, 0.11f, 0.16f, 1.0f };
//                                   R      G      B    알파
```

`{ 1.0f, 0.0f, 0.0f, 1.0f }` → 빨간 화면. 0~1 범위다.

**2. 창 크기 바꾸기** — `main.cpp`의 `kInitialWidth` / `kInitialHeight`

**3. 색이 매 프레임 변하게** — `Render()` 안

```cpp
static float t = 0.0f;
t += 0.01f;
const float color[4] = { sinf(t) * 0.5f + 0.5f, 0.2f, 0.4f, 1.0f };
m_context->ClearRenderTargetView(m_backBufferView.Get(), color);
```

게임 루프가 진짜로 계속 돌고 있다는 것을 눈으로 확인할 수 있다. (`#include <cmath>` 필요)

**4. `Present` 주석 처리하기**

```cpp
//m_swapChain->Present(1, 0);
```

색이 안 변하고, 창 제목의 FPS가 확 튄다.
`Present`가 **① 뒤집기와 ② 수직동기 대기를 둘 다** 한다는 것을 한 번에 볼 수 있다.

> `OMSetRenderTargets` 주석 처리는 지금 해도 아무 일이 없다. 위 "중요" 절 참고.
> 2단계에서 삼각형이 생긴 뒤에 하면 진짜로 깨진다.
