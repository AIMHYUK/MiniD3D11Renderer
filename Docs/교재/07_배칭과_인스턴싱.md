# 07. 배칭과 인스턴싱

> 상태: 진행중 · 갱신 2026-08-11 · 관련: [교재 목차](00_이_교재를_읽는_법.md), [06. 드로우 콜은 왜 비싼가](06_드로우콜은_왜_비싼가.md), [08. 계측](08_계측.md)
> 무엇: 드로우 콜 N개를 1개로 줄이는 두 가지 방법. 각각 어떻게 동작하고 언제 무엇을 고르는가.

---

## 1. 왜 필요한가

[06장](06_드로우콜은_왜_비싼가.md)에서 만든 버전은 스프라이트마다 `DrawIndexed`를 부른다.
10,000개면 10,000번이다.

그림 자체는 전부 같은 사각형이다. **같은 메시를 위치만 바꿔 반복하는 것**이라면
GPU에게 매번 따로 말할 이유가 없다.

---

## 2. 두 가지 방법

| | 동적 정점 버퍼 배칭 | 인스턴싱 |
|---|---|---|
| **아이디어** | CPU가 모든 정점을 큰 버퍼 하나에 모아 쓴다 | 정점은 한 벌만 두고 "인스턴스별 데이터"를 따로 넘긴다 |
| **정점 데이터** | N × 4개 (전부 실제로 씀) | 4개 (하나만) |
| **CPU 비용** | **높음** — 매 프레임 N×4개 정점 계산해서 쓰기 | **낮음** — N개 위치만 쓰기 |
| **유연성** | **높음** — 스프라이트마다 회전·크기·모양 자유 | 낮음 — 같은 메시여야 함 |
| **드로우 콜** | 1번 | 1번 |
| **잘 맞는 것** | 2D 스프라이트, UI, 파티클 | 같은 나무 1000그루, 총알, 잔디 |

**둘 다 드로우 콜은 1번**이다. 차이는 **CPU가 매 프레임 얼마나 많은 데이터를 쓰느냐**다.

> 실제 2D 엔진(유니티 SpriteRenderer, 언리얼 Slate)은 대체로 **동적 정점 배칭**을 쓴다.
> 스프라이트마다 크기·회전·UV가 제각각이라 인스턴싱의 제약이 불편하기 때문이다.
>
> 이 프로젝트에서는 **인스턴싱을 먼저 구현한다.** 코드가 짧고, 차이가 극적으로 드러나서
> 실험 대상으로 더 좋다. 시간이 남으면 배칭도 만들어 셋을 비교한다.

---

## 3. 인스턴싱 — 어떻게 동작하나

핵심 아이디어: **정점 버퍼를 두 개 꽂는다.**

```
슬롯 0 : 정점 버퍼 (4개)          ← 사각형 하나의 모양. 안 바뀜
         [좌상] [우상] [우하] [좌하]

슬롯 1 : 인스턴스 버퍼 (N개)      ← 스프라이트마다 다른 것. 매 프레임 갱신
         [위치·크기·색] [위치·크기·색] ... N개
```

GPU가 이렇게 돈다.

```
인스턴스 0에 대해:  정점 4개를 읽고, 인스턴스 데이터 0번을 함께 준다
인스턴스 1에 대해:  정점 4개를 읽고, 인스턴스 데이터 1번을 함께 준다
...
인스턴스 N-1까지
```

**정점 셰이더는 N × 4번 실행된다.** 매번 "이 정점" + "이 인스턴스의 위치"를 같이 받는다.

### 입력 레이아웃이 달라진다

```cpp
const D3D11_INPUT_ELEMENT_DESC layout[] = {
    // ── 슬롯 0: 정점당 ──
    { "POSITION", 0, DXGI_FORMAT_R32G32_FLOAT,       0,  0, D3D11_INPUT_PER_VERTEX_DATA,   0 },
    { "TEXCOORD", 0, DXGI_FORMAT_R32G32_FLOAT,       0,  8, D3D11_INPUT_PER_VERTEX_DATA,   0 },

    // ── 슬롯 1: 인스턴스당 ──
    { "IPOSSIZE", 0, DXGI_FORMAT_R32G32B32A32_FLOAT, 1,  0, D3D11_INPUT_PER_INSTANCE_DATA, 1 },
    { "ICOLOR",   0, DXGI_FORMAT_R32G32B32A32_FLOAT, 1, 16, D3D11_INPUT_PER_INSTANCE_DATA, 1 },
};
//                                                    ↑                    ↑              ↑
//                                              입력 슬롯          정점당/인스턴스당    스텝 레이트
```

바뀐 것 셋.

- **입력 슬롯**이 `0`과 `1`로 나뉜다 — 어느 버퍼에서 읽을지
- **`D3D11_INPUT_PER_INSTANCE_DATA`** — "이건 정점마다가 아니라 인스턴스마다 바뀐다"
- **스텝 레이트 `1`** — 인스턴스 1개마다 1칸씩 전진. (2면 인스턴스 2개마다 1칸)

HLSL에서는 그냥 입력이 늘어난 것처럼 보인다.

```hlsl
struct VSInput
{
    float2 position : POSITION;    // 정점당
    float2 uv       : TEXCOORD;    // 정점당
    float4 posSize  : IPOSSIZE;    // 인스턴스당  <- 셰이더는 구분 안 함
    float4 color    : ICOLOR;      // 인스턴스당
};
```

**셰이더는 이게 정점당인지 인스턴스당인지 모른다.** 입력 레이아웃이 알아서 채워 준다.

### 그리기

```cpp
ID3D11Buffer* buffers[] = { m_vertexBuffer.Get(), m_instanceBuffer.Get() };
UINT strides[] = { sizeof(Vertex), sizeof(InstanceData) };
UINT offsets[] = { 0, 0 };

m_context->IASetVertexBuffers(0, 2, buffers, strides, offsets);
m_context->IASetIndexBuffer(m_indexBuffer.Get(), DXGI_FORMAT_R16_UINT, 0);

m_context->DrawIndexedInstanced(
    6,      // 인스턴스 하나당 인덱스 개수 (사각형 = 6)
    N,      // 인스턴스 개수
    0, 0, 0);
```

**드로우 콜 1번.**

## 4. 인스턴스 버퍼 갱신 — `WRITE_DISCARD`가 여기서 결정적

매 프레임 N개 인스턴스 데이터를 GPU로 올려야 한다.

```cpp
D3D11_MAPPED_SUBRESOURCE mapped{};
m_context->Map(m_instanceBuffer.Get(), 0, D3D11_MAP_WRITE_DISCARD, 0, &mapped);
memcpy(mapped.pData, m_instanceData.data(), sizeof(InstanceData) * N);
m_context->Unmap(m_instanceBuffer.Get(), 0);
```

[03장](03_상수버퍼와_인덱스버퍼.md)에서 본 `WRITE_DISCARD`가 **여기서 진짜로 중요해진다.**

N이 10,000이면 이 버퍼가 수백 KB다. GPU가 아직 지난 프레임에 그 버퍼를 읽고 있는데
같은 메모리에 덮어쓰려 하면 **CPU가 GPU를 기다려야 한다.**

`WRITE_DISCARD`는 드라이버에게 "기존 내용 필요 없으니 빈 메모리를 새로 줘"라고 말한다.
드라이버가 버퍼를 여러 개 돌려쓰므로 **CPU가 안 기다린다.**

> 이걸 빼면 배칭을 했는데도 개별 드로우 콜보다 느려지는 일이 생긴다.
> **8장 실험에서 결과가 이상하면 1순위로 의심할 것.**

버퍼는 `DYNAMIC`으로, 최대 개수만큼 미리 크게 만들어 둔다.

```cpp
desc.Usage          = D3D11_USAGE_DYNAMIC;
desc.ByteWidth      = sizeof(InstanceData) * kMaxSprites;
desc.BindFlags      = D3D11_BIND_VERTEX_BUFFER;
desc.CPUAccessFlags = D3D11_CPU_ACCESS_WRITE;
```

**매 프레임 버퍼를 새로 만들면 안 된다.** 크게 한 번 만들고 앞부분만 쓴다.

## 5. 동적 정점 버퍼 배칭 (시간 남으면)

인스턴싱이 안 되는 경우 — 스프라이트마다 회전이 다르거나, 모양이 제각각이거나 —
CPU가 직접 모든 정점을 계산해 큰 버퍼에 채운다.

```cpp
// CPU에서 N개 스프라이트의 정점 4N개를 전부 계산
size_t v = 0;
for (const Sprite& s : m_sprites)
{
    vertices[v++] = { s.x,           s.y,            0, 0 };
    vertices[v++] = { s.x + s.width, s.y,            1, 0 };
    vertices[v++] = { s.x + s.width, s.y + s.height, 1, 1 };
    vertices[v++] = { s.x,           s.y + s.height, 0, 1 };
}
// 한 번에 올리고 한 번에 그린다
```

**드로우 콜은 1번이지만 CPU가 4배 많은 데이터를 쓴다.**
이것이 "배칭이 항상 이득은 아니다"의 근거다.
정점이 무거우면 모으는 비용이 드로우 콜을 줄인 이득을 넘어설 수 있다.

셋을 비교하면 실험이 훨씬 풍부해진다 — **개별 / 배칭 / 인스턴싱**.

---

## 6. 전환 가능하게 만들 것

**8장 실험의 전제다.** 같은 화면을 두 방식으로 그릴 수 있어야 비교가 성립한다.

```cpp
enum class DrawMode { Individual, Instanced };
DrawMode m_drawMode = DrawMode::Individual;
```

키보드로 전환하면 좋다 (`Window`의 `WM_KEYDOWN`에 이미 자리가 있다).
`Space`로 방식 전환, `↑`/`↓`로 N 조절. **눈으로 즉시 비교되면 실험이 빨라진다.**

**두 방식이 화면상 완전히 같은 결과를 내야 한다.** 이걸 먼저 확인하고 측정에 들어간다.
결과가 다르면 성능 비교에 의미가 없다.

---

## 7. 흔한 함정

| 증상 | 원인 |
|---|---|
| 인스턴스가 하나만 보임 | 스텝 레이트가 0이거나 `PER_VERTEX_DATA`로 돼 있음 |
| 전부 같은 자리에 겹침 | 인스턴스 버퍼를 안 꽂았거나 슬롯 번호가 틀림 |
| 아무것도 안 보임 | `IASetVertexBuffers`에 버퍼 개수를 2로 안 줌 |
| 배칭이 개별보다 느림 | `WRITE_DISCARD` 누락 — **1순위** |
| 일부만 보임 | 인스턴스 버퍼 크기 부족. `kMaxSprites` 확인 |
| N을 올리면 크래시 | 버퍼 크기를 넘겨 `memcpy` — 범위 검사 필요 |
| 프레임이 들쭉날쭉 | 매 프레임 버퍼를 새로 만들고 있음 |

## 8. 확인 문제

1. 인스턴싱에서 정점 버퍼와 인스턴스 버퍼는 각각 몇 개의 원소를 갖나? (스프라이트 N개 기준)
2. `D3D11_INPUT_PER_INSTANCE_DATA`와 스텝 레이트 1은 무슨 뜻인가?
3. 인스턴싱 시 정점 셰이더는 몇 번 실행되나?
4. 동적 정점 배칭이 인스턴싱보다 CPU 비용이 큰 이유는?
5. 배칭을 했는데 개별 드로우보다 느려졌다. 가장 먼저 볼 것은?

> 1번 답 — 정점 버퍼 **4개**(사각형 하나), 인스턴스 버퍼 **N개**.
>
> 3번 답 — **N × 4번.** 드로우 콜이 1번이라고 정점 셰이더도 한 번인 것은 아니다.
> 줄어든 것은 **CPU가 명령을 제출하는 횟수**지 GPU가 하는 일이 아니다.
> **6장의 "CPU 비용 vs GPU 비용" 구분이 여기서 다시 나온다.**
