# 03. 상수 버퍼와 인덱스 버퍼

> 상태: 진행중 · 갱신 2026-08-11 · 관련: [교재 목차](00_이_교재를_읽는_법.md), [02. 좌표계](02_좌표계.md), [04. 텍스처와 샘플러](04_텍스처와_샘플러.md)
> 무엇: C++에서 셰이더로 매 프레임 값을 넘기는 통로(상수 버퍼)와, 정점을 재사용해 사각형을 만드는 법(인덱스 버퍼).

---

## 1. 왜 필요한가

지금 삼각형은 **못 움직인다.** 좌표가 정점 버퍼에 `IMMUTABLE`로 박혀 있다.

스프라이트를 만들려면 매 프레임 위치를 바꿔 넣어야 한다.
그 통로가 **상수 버퍼**다.

그리고 스프라이트는 삼각형이 아니라 사각형이다.
사각형은 삼각형 2개인데, 정점을 6개 쓰면 낭비다. 그걸 줄이는 것이 **인덱스 버퍼**다.

---

## 2. 인덱스 버퍼 — 정점 재사용

사각형을 삼각형 2개로 만들면 정점이 6개 필요해 보인다.

```
   0 ────── 1        삼각형 A: 0, 1, 2
   │ ╲    A │        삼각형 B: 0, 2, 3
   │   ╲    │
   │ B   ╲  │        정점 0과 2가 양쪽에 들어간다
   3 ────── 2
```

그런데 **실제 정점은 4개뿐**이다. 0과 2가 두 번 쓰일 뿐이다.

인덱스 버퍼는 "정점 번호 목록"이다.

```cpp
Vertex vertices[4] = { ... };                    // 실제 데이터 4개
uint16_t indices[6] = { 0,1,2,  0,2,3 };         // 그리는 순서 6개
```

| | 정점 버퍼만 | 정점 + 인덱스 |
|---|---|---|
| 사각형 1개 | 정점 6개 (24바이트 × 6) | 정점 4개 + 인덱스 6개(2바이트씩) |
| 절약 | | 정점 2개분 |

**정점 하나가 커질수록 이득이 커진다.** 위치+UV+색+법선이면 정점 하나가 40바이트를 넘는다.
인덱스는 2바이트(`uint16`)라 훨씬 싸다.

캐릭터 메시처럼 정점 하나가 평균 4~6개 삼각형에 공유되는 경우 절약이 극적이다.

```cpp
m_context->IASetIndexBuffer(m_indexBuffer.Get(), DXGI_FORMAT_R16_UINT, 0);
m_context->DrawIndexed(6, 0, 0);   // Draw가 아니라 DrawIndexed
```

> 정점이 65,536개를 넘으면 `uint16`으로 부족해 `DXGI_FORMAT_R32_UINT`를 쓴다.
> 2D 스프라이트에서는 넘을 일이 거의 없다.

**순서는 여전히 시계 방향이어야 한다.** `0,1,2`와 `0,2,3` 둘 다 시계 방향인지 확인할 것.

## 3. 상수 버퍼 — C++에서 셰이더로

### 정점 버퍼와 무엇이 다른가

| | 정점 버퍼 | 상수 버퍼 |
|---|---|---|
| 무엇 | 정점마다 다른 값 | **모든 정점이 같이 쓰는 값** |
| 예 | 각 꼭짓점의 위치·색 | 화면 크기, 스프라이트 위치, 시간 |
| 크기 | 큼 (정점 수만큼) | 작음 (수십~수백 바이트) |
| 갱신 | 드물게 | **매 프레임** |

"이 드로우 콜 전체에 적용되는 설정값"이라고 보면 된다.

> **언리얼/유니티에서는** — 머티리얼 파라미터가 이것이다.
> Material Instance에서 색이나 스칼라를 바꾸면 상수 버퍼 내용이 바뀌는 것이다.

### HLSL 쪽

```hlsl
cbuffer SpriteConstants : register(b0)
{
    float2 screenSize;    //  8바이트
    float2 spritePos;     //  8바이트
    float2 spriteSize;    //  8바이트
    float2 padding;       //  8바이트  <- 채워 넣은 것
};                        // 합계 32바이트 (16의 배수)
```

`register(b0)`의 `b`는 buffer, `0`은 슬롯 번호다.
C++에서 `VSSetConstantBuffers(0, 1, ...)`의 첫 인자가 이 `0`과 짝을 이룬다.

### C++ 쪽

```cpp
struct SpriteConstants
{
    float screenWidth, screenHeight;
    float posX, posY;
    float sizeX, sizeY;
    float padding[2];        // HLSL과 똑같이 맞춘다
};
static_assert(sizeof(SpriteConstants) % 16 == 0, "상수 버퍼는 16바이트 배수여야 한다");
```

`static_assert`를 걸어두면 **컴파일 시점에** 걸린다. 런타임에 그림이 깨지고 나서 찾는 것보다 훨씬 낫다.

## 4. 16바이트 정렬 — 이 장의 진짜 함정

**상수 버퍼는 16바이트(float 4개) 단위로 끊어 읽는다.**
GPU 하드웨어가 그렇게 만들어져 있다.

그리고 규칙이 하나 더 있다.

> **하나의 변수가 16바이트 경계를 넘어가면 안 된다.
> 넘어갈 것 같으면 다음 경계로 밀려난다.**

이게 실수의 근원이다.

```hlsl
cbuffer Bad
{
    float2 a;      // 바이트 0~7
    float4 b;      // 8~23에 들어가야 하는데 16 경계를 넘음
                   // -> 실제로는 16~31로 밀려난다!
    float2 c;      // 32~39
};
```

C++에서 이렇게 쓰면 어긋난다.

```cpp
struct Bad {
    float a[2];    // 0~7
    float b[4];    // 8~23   <- 셰이더는 16~31에서 읽는다. 어긋남
    float c[2];
};
```

**증상이 고약하다.** 크래시가 안 난다. 그냥 **값이 이상하게 나온다.**
스프라이트가 엉뚱한 데 있거나, 크기가 이상하거나, 화면 밖으로 날아간다.

### 대처법 세 가지

**1. `float4` 단위로만 생각한다**
가장 안전하다. 애매하면 `float4`로 묶는다.

```hlsl
float4 screenAndPos;   // xy = 화면 크기, zw = 위치
float4 sizeAndPad;     // xy = 크기, zw = 미사용
```

**2. 작은 것끼리 짝지어 16을 채운다**
`float2` 둘 = 16바이트. `float3` + `float` = 16바이트.

**3. 명시적으로 padding을 넣는다**
위 예시가 이 방식이다. 읽기 쉬워서 추천.

> **디버그 요령** — 값이 이상하면 셰이더에서 그 값을 색으로 출력해 본다.
> `return float4(spritePos / screenSize, 0, 1);` 처럼.
> 눈으로 보면 "0이 들어왔네", "너무 크네"가 바로 보인다.
> 셰이더에는 `printf`가 없으니 **색이 곧 출력**이다. 이 습관을 들여두면 두고두고 쓴다.

## 5. 매 프레임 갱신하기 — Map / Unmap

```cpp
// 만들 때
D3D11_BUFFER_DESC desc{};
desc.ByteWidth      = sizeof(SpriteConstants);
desc.Usage          = D3D11_USAGE_DYNAMIC;          // CPU가 자주 쓴다
desc.BindFlags      = D3D11_BIND_CONSTANT_BUFFER;
desc.CPUAccessFlags = D3D11_CPU_ACCESS_WRITE;
m_device->CreateBuffer(&desc, nullptr, m_constantBuffer.GetAddressOf());
```

```cpp
// 매 프레임
D3D11_MAPPED_SUBRESOURCE mapped{};
m_context->Map(m_constantBuffer.Get(), 0, D3D11_MAP_WRITE_DISCARD, 0, &mapped);
memcpy(mapped.pData, &constants, sizeof(constants));
m_context->Unmap(m_constantBuffer.Get(), 0);

m_context->VSSetConstantBuffers(0, 1, m_constantBuffer.GetAddressOf());
```

### `WRITE_DISCARD`가 중요한 이유

**CPU와 GPU는 따로 논다.** 우리가 `Map`을 부르는 순간, GPU는 아직 몇 프레임 전 명령을
처리하고 있을 수 있다. 그 버퍼를 GPU가 읽는 중일지도 모른다.

| 플래그 | 뜻 | 결과 |
|---|---|---|
| `WRITE_DISCARD` | 기존 내용 버리고 **새 메모리를 줘** | 드라이버가 새 영역을 준다. 안 기다림 |
| `WRITE_NO_OVERWRITE` | 안 쓰던 부분에만 덧씀 | 안 기다림. 단 겹치면 책임은 우리 것 |
| (플래그 없음) | 그 메모리에 직접 씀 | **GPU가 끝날 때까지 기다림** ← 느림 |

`WRITE_DISCARD`를 쓰면 드라이버가 뒤에서 버퍼를 여러 개 돌려쓴다.
그래서 CPU가 GPU를 안 기다린다. 이걸 안 쓰면 프레임이 갑자기 반토막 난다.

**8장에서 이게 왜 성능에 결정적인지 다시 다룬다.**

## 6. 어느 셰이더에 꽂을지

```cpp
m_context->VSSetConstantBuffers(0, 1, ...);   // 정점 셰이더용
m_context->PSSetConstantBuffers(0, 1, ...);   // 픽셀 셰이더용
```

**둘은 별개 슬롯이다.** VS와 PS가 같은 상수 버퍼를 쓰려면 **둘 다 호출해야 한다.**
VS에만 꽂고 PS에서 읽으면 쓰레기 값이 나온다. 자주 겪는 실수다.

---

## 7. 흔한 함정 정리

| 증상 | 원인 |
|---|---|
| 값이 엉뚱함, 크래시는 없음 | **16바이트 정렬** — 1순위 의심 |
| PS에서 상수가 0 | `PSSetConstantBuffers`를 안 함 |
| 프레임이 갑자기 뚝뚝 끊김 | `Map`에 `WRITE_DISCARD`를 안 씀 |
| `Map`이 실패 | `Usage`가 `DYNAMIC`이 아니거나 `CPU_ACCESS_WRITE`가 없음 |
| 사각형이 안 보임 | 인덱스 순서가 반시계 |
| 사각형 절반만 보임 | 인덱스 6개 중 하나가 틀림 |

## 8. 확인 문제

1. 정점 버퍼와 상수 버퍼의 차이를 한 문장으로.
2. `float2` 3개만 든 상수 버퍼는 몇 바이트로 만들어야 하나? 왜인가?
3. `WRITE_DISCARD`를 안 쓰면 왜 느려지나?
4. VS에서는 상수가 잘 오는데 PS에서는 0이 나온다. 무엇을 빠뜨렸나?
5. 정점 24바이트짜리 메시가 정점 1,000개 / 삼각형 1,800개다.
   인덱스 버퍼를 쓸 때와 안 쓸 때 메모리는 각각 얼마인가?

> 2번 답 — `float2` 3개 = 24바이트지만 **32바이트**로 만든다. 16의 배수여야 한다.
>
> 5번 답 — 안 쓰면 정점 5,400개 × 24 = **129,600바이트**.
> 쓰면 1,000 × 24 + 5,400 × 2 = 24,000 + 10,800 = **34,800바이트**. 약 1/4로 준다.
