# 05. 블렌딩과 상태 객체

> 상태: 진행중 · 갱신 2026-08-11 · 관련: [교재 목차](00_이_교재를_읽는_법.md), [04. 텍스처와 샘플러](04_텍스처와_샘플러.md), [06. 드로우 콜은 왜 비싼가](06_드로우콜은_왜_비싼가.md)
> 무엇: 투명이 어떻게 계산되는지, 왜 그리는 순서가 중요한지, 그리고 D3D11이 설정을 "객체"로 만들게 하는 이유.

---

## 1. 왜 필요한가

투명 배경 PNG를 그냥 그리면 **배경이 검은 네모로 나온다.**
알파 채널이 있어도 D3D는 기본적으로 그것을 무시하고 덮어쓴다.

투명을 쓰려면 "새로 그리는 색"과 "이미 있던 색"을 **섞으라고** 알려줘야 한다.
그것이 블렌딩이고, OM(Output Merger) 단계에서 일어난다.

---

## 2. 알파 블렌딩 수식

```
결과 = 새 색 × SrcAlpha  +  기존 색 × (1 - SrcAlpha)
       └─ Source ─┘         └─ Destination ─┘
```

**Source**는 지금 픽셀 셰이더가 내놓은 색, **Destination**은 렌더 타깃에 이미 있던 색이다.

| SrcAlpha | 결과 |
|---|---|
| 1.0 | 새 색 100% (완전 불투명) |
| 0.5 | 반반 |
| 0.0 | 기존 색 그대로 (완전 투명) |

D3D는 이 수식을 일반화해서 각 항을 고를 수 있게 해 둔다.

```cpp
D3D11_RENDER_TARGET_BLEND_DESC& rt = desc.RenderTarget[0];
rt.BlendEnable    = TRUE;
rt.SrcBlend       = D3D11_BLEND_SRC_ALPHA;       // 새 색에 곱할 것
rt.DestBlend      = D3D11_BLEND_INV_SRC_ALPHA;   // 기존 색에 곱할 것 (1 - alpha)
rt.BlendOp        = D3D11_BLEND_OP_ADD;          // 둘을 더한다
rt.SrcBlendAlpha  = D3D11_BLEND_ONE;
rt.DestBlendAlpha = D3D11_BLEND_INV_SRC_ALPHA;
rt.BlendOpAlpha   = D3D11_BLEND_OP_ADD;
rt.RenderTargetWriteMask = D3D11_COLOR_WRITE_ENABLE_ALL;
```

### 다른 조합들

수식의 항만 바꾸면 다른 효과가 된다.

| 이름 | Src | Dest | 결과 |
|---|---|---|---|
| **알파 블렌드** | `SRC_ALPHA` | `INV_SRC_ALPHA` | 일반 투명 |
| **가산(Additive)** | `ONE` | `ONE` | 밝아지기만 함 — 불, 빛, 마법 |
| **곱셈(Multiply)** | `DEST_COLOR` | `ZERO` | 어두워지기만 함 — 그림자, 얼룩 |
| **불투명** | `ONE` | `ZERO` | 그냥 덮어쓰기 (블렌딩 끈 것과 같음) |

> **엔진에서는** — 머티리얼의 Blend Mode다.
> 언리얼: Opaque / Masked / Translucent / Additive / Modulate.
> 유니티: `Blend SrcAlpha OneMinusSrcAlpha` 같은 셰이더 구문.
> **정확히 같은 수식의 이름만 다른 것이다.**

---

## 3. 왜 순서가 중요한가

블렌딩 수식이 **"기존 색"을 읽는다**는 데 답이 있다.

```
빨강(알파 0.5)을 먼저, 파랑(알파 0.5)을 나중에
  → 파랑이 "빨강 위에" 섞인다

파랑을 먼저, 빨강을 나중에
  → 빨강이 "파랑 위에" 섞인다

결과가 다르다
```

불투명은 순서가 상관없다. 뒤에 그린 게 그냥 덮어쓰니까(+뎁스 테스트가 걸러주니까).
**투명은 순서가 결과를 바꾼다.**

그래서 3D 엔진은 이렇게 한다.

1. 불투명 물체를 **앞에서 뒤로** 그린다 (뎁스 테스트로 가려진 픽셀을 일찍 버리려고)
2. 투명 물체를 **뒤에서 앞으로** 정렬해 그린다

**이게 투명이 비싼 이유다.** 매 프레임 카메라 기준으로 정렬해야 하고, 정렬 순서가 곧 드로우 순서라
**배칭으로 묶기도 어렵다.** 6~7장의 배칭 이야기와 여기서 연결된다.

> "투명 오브젝트는 왜 따로 그리나요?"는 면접 단골 질문이다.
> 답: 블렌딩이 기존 픽셀을 읽으므로 순서에 의존하고, 뎁스 버퍼가 그 순서를 대신 해결해 주지 못하기 때문.

### 2D에서는

이 프로젝트는 2D라 뎁스 버퍼가 없다. **그린 순서가 곧 앞뒤 순서다.**
나중에 그린 게 위에 온다. 정렬은 배열 순서로 하면 된다.

## 4. 상태 객체 — 왜 매번 설정하지 않고 객체를 만드나

D3D11은 이런 설정들을 **객체로 만들어 두고 꽂는** 방식이다.

| 객체 | 무엇을 정하나 | 파이프라인 단계 |
|---|---|---|
| `ID3D11BlendState` | 색을 어떻게 섞을지 | OM |
| `ID3D11DepthStencilState` | 뎁스 테스트를 할지, 어떻게 | OM |
| `ID3D11RasterizerState` | 컬링 방향, 채우기 모드, 시저 | RS |
| `ID3D11SamplerState` | 텍스처를 어떻게 읽을지 | PS |

이유가 둘이다.

**1. 검증을 만들 때 한 번만 한다.**
설정 조합이 유효한지 검사하는 비용을 `Create` 시점에 몰아넣는다.
매 프레임 `Set`할 때는 이미 검증된 것을 꽂기만 하므로 싸다.

**2. 드라이버가 미리 GPU 명령으로 굳혀둘 수 있다.**
`Set`은 그 굳혀둔 것을 가리키기만 하면 된다.

> **그래서 상태 객체는 초기화 때 다 만들어 두고 재사용한다.**
> 매 프레임 `CreateBlendState`를 부르면 안 된다. 이건 실수가 아니라 재앙이다.

### 상태 변경도 공짜가 아니다

`Set`이 싸다고 했지만 **0은 아니다.** GPU 파이프라인 설정이 바뀌면 내부적으로 정리가 일어난다.

그래서 렌더링 순서를 짤 때 **같은 상태끼리 묶는다.**

```
나쁨:  블렌드ON → OFF → ON → OFF ...   (상태 변경 N번)
좋음:  불투명 전부(OFF) → 투명 전부(ON)  (상태 변경 1번)
```

> **언리얼에서는** — `stat rhi`의 **State Change** 항목이 이 횟수다.
> 유니티 Profiler의 **SetPass Calls**가 비슷한 개념이다.
> "Draw Call보다 SetPass Call이 더 중요하다"는 말이 여기서 나온다.

**6장의 드로우 콜 비용과 직접 이어지는 대목이다.**

## 5. 코드로는

```cpp
// 초기화 때 한 번
D3D11_BLEND_DESC desc{};
desc.RenderTarget[0].BlendEnable = TRUE;
// ... 위 설정 ...
m_device->CreateBlendState(&desc, m_alphaBlend.GetAddressOf());
```

```cpp
// 매 프레임 (또는 상태가 바뀔 때만)
const float blendFactor[4] = { 0, 0, 0, 0 };
m_context->OMSetBlendState(m_alphaBlend.Get(), blendFactor, 0xFFFFFFFF);
```

마지막 인자 `0xFFFFFFFF`는 **샘플 마스크**다. MSAA에서 어느 샘플을 쓸지 고르는 것으로,
MSAA를 안 쓰면 전부 켜두면 된다. (플립 모델이라 어차피 MSAA를 못 쓴다)

`blendFactor`는 `D3D11_BLEND_BLEND_FACTOR`를 쓸 때만 의미가 있다. 지금은 무시된다.

## 6. 미리 곱해진 알파 (Premultiplied Alpha)

알아두면 좋은 함정이다.

일반 알파 블렌딩은 텍스처의 RGB가 **알파와 무관하게** 저장돼 있다고 가정한다.
그런데 투명 픽셀의 RGB가 검정(0,0,0)으로 저장된 PNG가 흔하다.

그러면 **가장자리에 검은 테두리**가 생긴다. 보간 과정에서 투명한 검정이 섞여 들어오기 때문이다.

해법 둘.
- 텍스처를 만들 때 RGB에 알파를 미리 곱해두고, `SrcBlend`를 `ONE`으로 (미리 곱한 알파)
- 또는 투명 영역의 RGB를 인접 색으로 채워 둔다 (아트 쪽 처리)

> 스프라이트 가장자리가 거뭇하면 이걸 의심한다.
> 지금 프로젝트에서 겪을 확률은 낮지만, 겪으면 원인을 못 찾아 한참 헤맨다.

---

## 7. 흔한 함정

| 증상 | 원인 |
|---|---|
| 투명 PNG가 검은 네모로 | `BlendEnable`이 FALSE 또는 `OMSetBlendState` 누락 |
| 아무것도 안 보임 | PS가 알파 0을 반환. 텍스처 알파를 확인 |
| 겹친 순서가 이상함 | 그리는 순서 문제. 2D는 배열 순서 = 앞뒤 |
| 스프라이트 가장자리가 거뭇함 | 미리 곱해진 알파 문제 |
| 프레임이 급락 | 매 프레임 `CreateBlendState`를 부르고 있음 |
| 반투명이 너무 진하거나 옅음 | `SrcBlend`/`DestBlend` 조합 확인 |

## 8. 확인 문제

1. 알파 블렌딩 수식을 쓰고, 각 항이 무엇인지 말하라.
2. 불투명 물체는 순서가 상관없는데 투명은 왜 상관있나?
3. 가산 블렌딩(`ONE`, `ONE`)은 어떤 효과에 쓰나? 왜 그 효과에 맞나?
4. 상태 객체를 매 프레임 만들면 왜 안 되나?
5. 드로우 콜 수는 같은데 프레임이 느리다. 상태 변경 쪽에서 의심할 것은?

> 3번 답 — 불·빛·마법 이펙트. 항상 밝아지기만 하고 어두워지지 않아서
> "빛이 더해진다"는 물리적 직관과 맞는다. 게다가 **순서에 무관하다** (덧셈은 교환법칙이 성립).
> 그래서 정렬 없이 그려도 결과가 같다 — 투명인데도 싼 이유.
