# 06. 드로우 콜은 왜 비싼가

> 상태: 진행중 · 갱신 2026-08-11 · 관련: [교재 목차](00_이_교재를_읽는_법.md), [05. 블렌딩과 상태 객체](05_블렌딩과_상태객체.md), [07. 배칭과 인스턴싱](07_배칭과_인스턴싱.md)
> 무엇: `Draw()` 한 번에 실제로 무슨 비용이 드는지. "드로우 콜을 줄여라"가 왜 렌더링 최적화의 첫 문장인지.

**이 장부터가 이 프로젝트의 목적지다.** 앞의 다섯 장은 여기 오기 위한 준비였다.

---

## 1. 왜 필요한가

면접에서 거의 반드시 나온다.

> "드로우 콜을 줄이는 방법은 무엇이 있나요?"
> "프레임 드랍이 났을 때 CPU 바운드인지 GPU 바운드인지 어떻게 판단하죠?"

그리고 네오플 업무 내용이 **"유저 환경 최적화를 위한 메모리/렌더링 최적화"**다.
스마일게이트 5912 우대사항이 **"다양한 OS/플랫폼에서 프로파일링 수행 및 최적화"**다.

---

## 2. `Draw()`를 부르면 실제로 무슨 일이 나나

**그림이 그려지지 않는다.** 이게 핵심이다.

```
우리 코드          Draw() 호출
   ↓
D3D11 런타임       인자 검증, 상태 확인
   ↓
그래픽 드라이버     GPU가 알아듣는 명령으로 번역
   ↓
커맨드 버퍼        명령을 줄 세워 쌓아둠
   ↓
   ...             (나중에)
   ↓
GPU               실제로 그림
```

`Draw()`는 **"이거 그려줘"라는 쪽지를 큐에 넣고 즉시 돌아온다.**
GPU는 그 쪽지를 몇 밀리초 뒤에, 몇 프레임 뒤에 꺼내 처리할 수도 있다.

**그래서 드로우 콜 비용은 두 종류다.**

| | 어디서 | 무엇 |
|---|---|---|
| **CPU 비용** | 우리 코드~드라이버 | 검증, 번역, 명령 기록 |
| **GPU 비용** | GPU | 실제 정점·픽셀 처리 |

"드로우 콜이 비싸다"고 할 때 말하는 것은 **거의 항상 CPU 비용**이다.

---

## 3. CPU 비용의 정체

`Draw()` 하나가 CPU에서 대략 이런 일을 한다.

1. **런타임 검증** — 셰이더와 입력 레이아웃이 맞나, 바인딩이 유효한가
2. **상태 비교** — 지난 드로우와 무엇이 바뀌었나
3. **명령 번역** — 바뀐 것을 GPU 명령으로 바꿔 커맨드 버퍼에 기록
4. **커널 전환** — 주기적으로 커맨드 버퍼를 GPU에 제출

하나하나는 마이크로초 단위다. 그런데 **10,000번이면 이야기가 달라진다.**

```
드로우 콜 하나에 CPU 5마이크로초라고 하면

   1,000개  →   5ms   (60fps 예산 16.6ms 중 30%)
  10,000개  →  50ms   (예산 초과. 20fps)
```

**GPU는 놀고 있는데 CPU가 명령을 못 대준다.** 이것이 **CPU 바운드**다.

### 상태 변경이 더 비싸다

같은 드로우 콜이라도 그 사이에 무엇이 바뀌었느냐로 비용이 크게 달라진다.

```
싼 것:  같은 셰이더, 같은 텍스처, 상수 버퍼만 바뀜
비쌈:   셰이더 교체, 텍스처 교체, 블렌드 상태 교체
```

[05장](05_블렌딩과_상태객체.md)에서 "같은 상태끼리 묶는다"고 한 이유다.

> **유니티에서 SetPass Call이 Draw Call보다 중요하다**고 하는 게 이 이야기다.
> 언리얼 `stat rhi`의 State Change도 같은 것이다.

---

## 4. CPU 바운드와 GPU 바운드

성능 문제를 만나면 **제일 먼저 갈라야 하는 것**이다. 진단이 반대면 최적화가 전부 헛수고다.

| | CPU 바운드 | GPU 바운드 |
|---|---|---|
| 무엇이 병목 | 명령을 만드는 쪽 | 명령을 처리하는 쪽 |
| 증상 | 드로우 콜·오브젝트 수가 늘면 급격히 느려짐 | 해상도를 올리면 급격히 느려짐 |
| 해상도를 낮추면 | **거의 안 변함** | 빨라짐 |
| 오브젝트를 반으로 줄이면 | 빨라짐 | 거의 안 변함 |
| 해법 | **배칭, 인스턴싱**, 컬링 | 셰이더 단순화, 오버드로우 감소, 해상도 |

**현장에서 가장 빠른 판별법**

> 해상도를 절반으로 줄여 본다.
> - 빨라지면 → GPU 바운드 (픽셀 처리가 병목)
> - 그대로면 → CPU 바운드 (명령 제출이 병목)

픽셀 수가 1/4로 줄어도 드로우 콜 수는 그대로이기 때문이다.
이 한 줄이 면접에서 바로 쓸 수 있는 답이다.

---

## 5. 그래서 줄이는 방법들

| 방법 | 무엇 | 이 프로젝트에서 |
|---|---|---|
| **배칭** | 여러 물체의 정점을 한 버퍼에 모아 한 번에 | **7장** |
| **인스턴싱** | 같은 메시를 N개 한 번에 | **7장** |
| 텍스처 아틀라스 | 여러 그림을 한 장에 모아 텍스처 교체를 없앰 | 다루지 않음 |
| 정렬 | 같은 상태끼리 묶어 상태 변경 최소화 | 5장에서 언급 |
| 컬링 | 안 보이는 건 아예 안 그림 | 다루지 않음 |
| LOD | 멀면 단순한 메시로 | 다루지 않음 |

> **엔진에서는** — 언리얼의 Static Batching, Instanced Static Mesh, Auto Instancing,
> 유니티의 SRP Batcher, GPU Instancing, Static/Dynamic Batching.
> **전부 "드로우 콜 수를 줄인다"는 한 가지 목적의 다른 구현이다.**
>
> 지금까지 이걸 체크박스로만 켜봤다면, 7장에서 그 안을 직접 만든다.

## 6. 이번 단계에서 만들 것

**아직 최적화하지 않는다.** 느린 버전을 먼저 만든다.

```cpp
for (const Sprite& s : m_sprites)
{
    // 스프라이트마다 상수 버퍼를 갱신하고
    UpdateConstantBuffer(s);
    // 스프라이트마다 드로우 콜
    m_context->DrawIndexed(6, 0, 0);
}
```

N을 쉽게 바꿀 수 있게 해 둔다. 100, 1000, 10000.

**느린 게 정상이다.** 7장에서 빠르게 만들고, 8장에서 그 차이를 잰다.
**비교 대상이 없으면 실험이 성립하지 않는다.**

### 스프라이트 구조

```cpp
struct Sprite
{
    float x, y;          // 화면 픽셀 좌표
    float width, height;
    float r, g, b, a;     // 틴트 색
};
std::vector<Sprite> m_sprites;
```

위치를 무작위로 흩뿌리되, **매 실행마다 같은 배치가 나오게 시드를 고정한다.**
안 그러면 측정할 때마다 조건이 달라져 비교가 안 된다.

```cpp
std::mt19937 rng(12345);   // 고정 시드
```

> 사소해 보이지만 실험 설계의 기본이다. MiniOscReceiver에서 부하를 고정한 것과 같은 이유다.

## 7. 흔한 오해

**"드로우 콜은 무조건 적을수록 좋다"**
→ 아니다. **GPU 바운드면 드로우 콜을 줄여도 안 빨라진다.**
1,000개를 1개로 합쳤는데 그리는 픽셀 수가 같으면 GPU 시간은 그대로다.
진단이 먼저다.

**"드로우 콜 = GPU 부하"**
→ 아니다. 대부분 CPU 부하다.

**"배칭하면 항상 이득"**
→ 아니다. 정점을 모으는 CPU 비용이 드로우 콜을 줄인 이득보다 클 수 있다.
**7장에서 실제로 이 지점을 찾는다.** 그게 이 프로젝트의 핵심 질문이다.

**"드로우 콜 N개면 CPU 비용도 정확히 N배"**
→ 대략 비례하지만 정확히는 아니다. 상태 변경 여부에 따라 크게 달라진다.

## 8. 확인 문제

1. `Draw()`가 반환된 시점에 그림이 그려져 있나?
2. 드로우 콜 비용은 주로 CPU 쪽인가 GPU 쪽인가? 왜인가?
3. 해상도를 절반으로 줄였더니 프레임이 그대로다. CPU 바운드인가 GPU 바운드인가?
4. 드로우 콜 수는 같은데 A 장면이 B 장면보다 느리다. 무엇을 의심하나?
5. 드로우 콜을 1,000개에서 1개로 줄였는데 프레임이 그대로다. 왜 그럴 수 있나?

> 3번 답 — **CPU 바운드.** 해상도를 줄이면 픽셀 처리(GPU)가 줄어드는데 변화가 없다는 것은
> 병목이 픽셀 쪽이 아니라는 뜻이다.
>
> 5번 답 — 원래부터 GPU 바운드였을 가능성. 드로우 콜을 합쳐도 그리는 픽셀 수는 그대로라
> GPU 시간이 안 준다. 또는 애초에 1,000개로도 CPU가 여유로웠을 수도 있다.
> **8장의 실험이 정확히 이 경계를 찾는 것이다.**
