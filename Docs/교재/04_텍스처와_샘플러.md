# 04. 텍스처와 샘플러

> 상태: 진행중 · 갱신 2026-08-11 · 관련: [교재 목차](00_이_교재를_읽는_법.md), [03. 상수 버퍼와 인덱스 버퍼](03_상수버퍼와_인덱스버퍼.md), [05. 블렌딩과 상태 객체](05_블렌딩과_상태객체.md)
> 무엇: 이미지 파일이 GPU 메모리에 올라가 픽셀 셰이더에서 읽히기까지. UV 좌표, 샘플러, 밉맵.

---

## 1. 왜 필요한가

색이 정점에서 오면 표현할 수 있는 게 거의 없다. 캐릭터도 배경도 UI도 전부 그림이다.
**그림을 GPU로 올려 픽셀마다 알맞은 위치를 읽어오는 것**이 이 장의 주제다.

그리고 여기서부터 **스프라이트**가 된다. 4~8장의 실험 대상이 여기서 생긴다.

---

## 2. UV 좌표 — 텍스처 안의 주소

텍스처 안의 위치를 가리키는 좌표다. **해상도와 무관하게 0~1**이다.

```
 (0,0) ┌─────────────┐ (1,0)
       │             │
       │      ·      │  (0.5, 0.5) = 한가운데
       │             │
 (0,1) └─────────────┘ (1,1)
```

| | 방향 |
|---|---|
| u | 오른쪽이 + |
| v | **아래가 +** |

**NDC와 y 방향이 반대다.** [02장](02_좌표계.md)에서 짚은 그것이다.
NDC는 위가 +, UV는 아래가 +. 여기서 뒤집힌 텍스처가 나온다.

**해상도와 무관한 이유**는 NDC와 같다. 512×512든 2048×2048든 "오른쪽 아래 구석"은 `(1,1)`이다.
텍스처를 교체해도 UV는 안 고쳐도 된다.

### 정점에 UV를 넣는다

```cpp
struct Vertex {
    float x, y;      // 위치
    float u, v;      // UV      <- 추가
};
```

**[01장](01_그림이_화면에_나오기까지.md)에서 말한 "셋을 같이 고친다"가 여기서 처음 실전으로 온다.**
C++ 구조체 / 입력 레이아웃 / HLSL `VSInput` 세 군데 전부.

사각형 네 꼭짓점에만 UV를 주면 **안쪽 픽셀은 RS가 보간해 준다.** 색 그라데이션과 같은 원리다.

---

## 3. 세 가지가 필요하다

텍스처를 쓰려면 객체가 셋 필요하다. 처음에 헷갈리는 부분이다.

| 객체 | 무엇 | 비유 |
|---|---|---|
| `ID3D11Texture2D` | **데이터** — GPU 메모리에 올라간 픽셀 덩어리 | 책 |
| `ID3D11ShaderResourceView` | **"이걸 읽는 재료로 쓴다"는 꼬리표** | 도서 대출증 |
| `ID3D11SamplerState` | **어떻게 읽을지의 규칙** | 읽는 방법 (돋보기? 대충?) |

[00장](00_이_교재를_읽는_법.md)에서 본 뷰(View) 이야기가 다시 나온다.
같은 텍스처를 **그리는 대상**(RTV)으로도 **읽는 재료**(SRV)로도 쓸 수 있으니, 용도를 꼬리표로 구분한다.

```cpp
m_context->PSSetShaderResources(0, 1, m_textureView.GetAddressOf());  // SRV
m_context->PSSetSamplers(0, 1, m_sampler.GetAddressOf());             // 샘플러
```

```hlsl
Texture2D    diffuseMap : register(t0);   // t = texture
SamplerState linearClamp : register(s0);  // s = sampler

float4 color = diffuseMap.Sample(linearClamp, input.uv);
```

`t0`, `s0`의 숫자가 C++ 첫 인자의 슬롯 번호와 짝을 이룬다. 상수 버퍼의 `b0`와 같은 방식이다.

---

## 4. 샘플러 — 어떻게 읽을 것인가

UV `(0.5, 0.5)`가 정확히 픽셀 하나를 가리키는 경우는 드물다. 대개 픽셀 사이에 떨어진다.
그때 어떻게 할지가 샘플러 설정이다.

### 필터

| 필터 | 동작 | 쓰는 곳 |
|---|---|---|
| `POINT` | 가장 가까운 픽셀 하나를 그대로 | **픽셀아트**, 확대해도 네모나게 |
| `LINEAR` | 주변 4개를 섞음 | 일반적인 그림. 부드럽게 |
| `ANISOTROPIC` | 비스듬히 볼 때 보정 | 3D 바닥·벽 |

**픽셀아트를 `LINEAR`로 그리면 뭉개져 보인다.** 반대로 사진을 `POINT`로 확대하면 계단이 진다.
2D 스프라이트라면 원본 크기로 쓸 땐 아무거나, 확대할 거면 의도에 맞게 고른다.

### 주소 모드 — UV가 0~1을 벗어나면

| 모드 | 동작 |
|---|---|
| `WRAP` | 반복. `1.3` → `0.3` (타일링 바닥) |
| `CLAMP` | 가장자리에 붙임. `1.3` → `1.0` |
| `MIRROR` | 뒤집어 반복 |
| `BORDER` | 지정한 색 |

스프라이트는 보통 `CLAMP`다. `WRAP`으로 두면 UV가 살짝 넘칠 때 반대편 픽셀이 딸려온다.

```cpp
D3D11_SAMPLER_DESC desc{};
desc.Filter   = D3D11_FILTER_MIN_MAG_MIP_LINEAR;
desc.AddressU = D3D11_TEXTURE_ADDRESS_CLAMP;
desc.AddressV = D3D11_TEXTURE_ADDRESS_CLAMP;
desc.AddressW = D3D11_TEXTURE_ADDRESS_CLAMP;
desc.MaxLOD   = D3D11_FLOAT32_MAX;
m_device->CreateSamplerState(&desc, m_sampler.GetAddressOf());
```

> `MIN_MAG_MIP_LINEAR`의 셋은 각각 **축소(Minification) / 확대(Magnification) / 밉맵 사이**의 필터다.
> 따로 지정할 수 있다는 뜻이다.

## 5. 밉맵 — 축소할 때의 문제

1024×1024 텍스처를 화면에서 64×64로 그린다고 하자.
픽셀 하나가 텍스처의 16×16 영역을 대표해야 하는데, 샘플러는 **한 점만 읽는다.**

결과는 **깜빡임(aliasing)**이다. 카메라가 조금만 움직여도 읽는 점이 바뀌어 지글거린다.

밉맵은 **미리 줄여둔 사본들**이다.

```
1024 → 512 → 256 → 128 → 64 → 32 → ... → 1
```

GPU가 화면 크기에 맞는 단계를 골라 읽는다. 지글거림이 사라진다.

**비용은 메모리 약 +33%다.** (1/4 + 1/16 + 1/64 + ... ≈ 1/3)
그 대신 **캐시 적중률이 올라 오히려 빨라지는 경우가 많다.** 멀리 있는 물체가 작은 텍스처를 읽으니까.

> **엔진에서는** — 텍스처 임포트 설정의 Generate Mip Maps가 이것이다.
> UI 텍스처는 항상 원본 크기로 그리므로 보통 끈다.

지금 프로젝트는 스프라이트를 원본 크기 근처로 그리므로 **밉맵 없이 시작해도 된다.**
시간이 남으면 붙인다.

## 6. WIC로 PNG 읽기

Windows에 내장된 이미지 디코더다. **외부 라이브러리가 필요 없다.**
(`stb_image.h` 같은 단일 헤더를 쓰면 훨씬 짧지만, WIC를 쓰면 그 자체가
"Windows 시스템 프로그래밍" 경험으로 남는다 — 스마일게이트 6098 자격요건에 그 항목이 있다.)

흐름은 이렇다.

```
CoInitializeEx                      COM 초기화 (WIC이 COM 기반)
  └ IWICImagingFactory 생성
      └ CreateDecoderFromFilename   파일 열기
          └ GetFrame(0)             첫 프레임 (GIF은 여러 장일 수 있음)
              └ WICConvertBitmapSource  RGBA 32비트로 변환
                  └ CopyPixels      바이트 배열로 받기
                      └ CreateTexture2D  GPU로 올리기
```

**포맷 변환을 반드시 거친다.** PNG는 팔레트·그레이스케일·16비트 등 형태가 여러 가지인데,
`GUID_WICPixelFormat32bppRGBA`로 통일해 두면 이후가 단순해진다.

```cpp
D3D11_TEXTURE2D_DESC desc{};
desc.Width      = width;
desc.Height     = height;
desc.MipLevels  = 1;                          // 밉맵 없이
desc.ArraySize  = 1;
desc.Format     = DXGI_FORMAT_R8G8B8A8_UNORM;
desc.SampleDesc.Count = 1;
desc.Usage      = D3D11_USAGE_IMMUTABLE;      // 안 바뀜
desc.BindFlags  = D3D11_BIND_SHADER_RESOURCE;

D3D11_SUBRESOURCE_DATA init{};
init.pSysMem     = pixels.data();
init.SysMemPitch = width * 4;    // <- 한 줄이 몇 바이트인지. 필수
```

`SysMemPitch`를 빼먹으면 그림이 대각선으로 밀린다. 아주 흔한 실수다.

> **2시간 규칙 적용 지점.** WIC 코드는 COM까지 얽혀서 장황하다.
> 여기서 2시간 넘게 막히면 **코드로 만든 체커보드 텍스처**로 넘어간다.
>
> ```cpp
> std::vector<uint32_t> pixels(64 * 64);
> for (int y = 0; y < 64; ++y)
>     for (int x = 0; x < 64; ++x)
>         pixels[y*64 + x] = ((x/8 + y/8) % 2) ? 0xFFFFFFFF : 0xFF404040;
> ```
>
> **텍스처를 어디서 얻느냐는 이 프로젝트의 본질이 아니다.** 배칭 실험에는 아무 텍스처나 된다.
> 오히려 체커보드가 샘플러 필터 차이를 눈으로 보기에는 더 좋다.

## 7. 흔한 함정

| 증상 | 원인 |
|---|---|
| 그림이 위아래 뒤집힘 | UV의 v 방향. NDC와 반대다 |
| 그림이 대각선으로 밀림 | `SysMemPitch`를 안 넣었거나 틀림 |
| 새까맣게 나옴 | `PSSetShaderResources` 또는 `PSSetSamplers` 누락 |
| 새까만데 알파는 있음 | 샘플러를 안 꽂음. 샘플 결과가 0 |
| 가장자리에 반대편 픽셀이 딸려옴 | 주소 모드가 `WRAP`. `CLAMP`로 |
| 확대하니 뭉개짐 / 계단짐 | 필터가 의도와 반대 (`LINEAR` ↔ `POINT`) |
| 멀리서 지글거림 | 밉맵 없음 |
| `CreateDecoderFromFilename` 실패 | `CoInitializeEx`를 안 불렀거나 경로가 틀림 |

**경로 문제는 [2단계에서 만든 `ResolvePathFromExe`](../작업일지/2026-08-11_2단계_파이프라인과_삼각형.md)를 그대로 쓴다.**
셰이더와 같은 이유로 텍스처도 exe 기준 경로여야 한다.

## 8. 확인 문제

1. 텍스처 하나를 쓰는 데 D3D11 객체가 셋 필요하다. 각각 무엇이고 왜 나뉘어 있나?
2. UV가 0~1로 정규화된 이유는? NDC와 같은 이유인가?
3. 픽셀아트 게임에서 샘플러 필터를 무엇으로 해야 하나? 왜인가?
4. 밉맵은 메모리를 약 33% 더 쓰는데 오히려 빨라질 수 있다. 왜인가?
5. 텍스처는 잘 로드됐는데 화면이 새까맣다. 확인할 것 세 가지는?

> 4번 답 — 멀리 있는 물체가 작은 밉 단계를 읽으므로 **텍스처 캐시 적중률이 올라간다.**
> 원본을 띄엄띄엄 읽으면 캐시가 계속 빗나가는데, 작은 사본은 통째로 캐시에 들어간다.
> 메모리 총량은 늘지만 실제 읽기는 빨라진다.
