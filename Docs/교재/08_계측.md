# 08. 계측 — 숫자로 말하기

> 상태: 진행중 · 갱신 2026-08-11 · 관련: [교재 목차](00_이_교재를_읽는_법.md), [07. 배칭과 인스턴싱](07_배칭과_인스턴싱.md), [공부 로드맵](../공부_로드맵.md)
> 무엇: 두 방식의 성능 차이를 믿을 수 있는 숫자로 만드는 법. 무엇을 재고, 어떻게 재고, 어디서 틀리는가.

**이 장이 이 프로젝트의 목적지다.** 포트폴리오의 핵심 한 줄이 여기서 나온다.

---

## 1. 왜 필요한가

"배칭하면 빨라집니다"는 누구나 한다. **면접에서 갈리는 것은 그다음이다.**

> "몇 개부터 차이가 났나요?"
> "왜 하필 거기서 갈렸다고 생각하세요?"
> "그때 CPU가 병목이었나요, GPU가 병목이었나요?"

숫자와 해석이 있으면 이 대화가 5분 이상 이어진다. 없으면 한 줄에 끝난다.

MiniOscReceiver에서 이미 한 방식이다. **같은 구조를 렌더링에서 반복하는 것**이고,
그 반복 자체가 "이 사람은 항상 이렇게 일한다"는 신호가 된다.

---

## 2. CPU와 GPU는 따로 논다

계측의 모든 어려움이 여기서 나온다.

```
CPU 타임라인   [프레임 5 명령 기록] [프레임 6 명령 기록] ...
                        ↓ 제출              ↓
GPU 타임라인        [프레임 3 그리는 중] [프레임 4 그리는 중] ...
                    └─ 몇 프레임 뒤처져 있다 ─┘
```

그래서 이런 일이 벌어진다.

```cpp
auto start = now();
m_context->DrawIndexed(...);      // 쪽지를 큐에 넣기만 함
auto end = now();
// end - start = 거의 0. GPU가 얼마나 걸리는지 전혀 알 수 없다
```

**`Draw()`를 감싸서 시간을 재면 CPU 제출 비용만 나온다.** GPU 시간이 아니다.
이걸 모르면 "인스턴싱이 100배 빠르다" 같은 엉터리 결론이 나온다.

---

## 3. 무엇을 재야 하나

세 가지가 다르고, 셋 다 의미가 있다.

| 재는 것 | 방법 | 알 수 있는 것 |
|---|---|---|
| **프레임 시간** | `Present` 사이의 벽시계 시간 | 최종 체감 성능. 제일 중요 |
| **CPU 제출 시간** | 드로우 루프 앞뒤로 QPC | 드로우 콜의 CPU 비용 |
| **GPU 실행 시간** | 타임스탬프 쿼리 | GPU가 실제로 그린 시간 |

**세 개를 같이 재야 CPU 바운드인지 GPU 바운드인지 말할 수 있다.**

```
프레임 16ms, CPU 제출 14ms, GPU 3ms   →  CPU 바운드
프레임 16ms, CPU 제출  1ms, GPU 15ms  →  GPU 바운드
```

이 표 하나가 [06장](06_드로우콜은_왜_비싼가.md)의 이론을 실측으로 바꾼다.

---

## 4. 반드시 먼저 — VSync를 끈다

```cpp
m_swapChain->Present(0, 0);   // 1이 아니라 0
```

**이걸 안 하면 실험 전체가 무의미해진다.**

VSync가 켜져 있으면 `Present`가 다음 화면 갱신까지 잠든다.
GPU가 3ms에 끝내든 6ms에 끝내든 **똑같이 6.94ms(144Hz)가 나온다.**
남는 시간이 전부 대기로 흡수되기 때문이다.

```
VSync ON:   개별 144 FPS,  인스턴싱 144 FPS   → "차이 없음" (틀린 결론)
VSync OFF:  개별  62 FPS,  인스턴싱 890 FPS   → 진짜 차이
```

> MiniOscReceiver에서 **저부하로 재고 "세 방식이 똑같다"고 착각했던 것과 같은 종류의 실수**다.
> 그때는 부하가 문제였고 이번엔 측정 조건이 문제다. 둘 다 "측정이 차이를 못 보는 상태".

---

## 5. 프레임 시간 재기

`FrameTimer`를 확장한다. 이미 `QueryPerformanceCounter`를 쓰고 있다.

```cpp
class FrameStats
{
public:
    void AddSample(double ms)
    {
        m_samples.push_back(ms);
    }

    // 워밍업 구간을 버린다 — 아래 7번 참고
    void Report(int discardFirst = 60)
    {
        std::vector<double> s(m_samples.begin() + discardFirst, m_samples.end());
        std::sort(s.begin(), s.end());

        double sum = 0;
        for (double v : s) sum += v;

        m_avg    = sum / s.size();
        m_min    = s.front();
        m_max    = s.back();
        m_median = s[s.size() / 2];
        m_p99    = s[(size_t)(s.size() * 0.99)];
    }
    // ...
};
```

### 평균만 보면 안 되는 이유

```
방식 A:  평균 10ms,  최대 11ms    →  꾸준함
방식 B:  평균 10ms,  최대 60ms    →  가끔 뚝뚝 끊김
```

평균이 같아도 **B는 게임으로 못 쓴다.** 60ms 한 번이 눈에 보이는 끊김이다.

그래서 **중앙값과 99 퍼센타일(p99)**을 같이 본다.
p99는 "100 프레임 중 가장 느린 1개"의 시간이다. 체감 끊김과 직결된다.

> 실무에서 "평균 FPS"보다 "1% low"를 보는 이유가 이것이다.

## 6. GPU 시간 재기 — 타임스탬프 쿼리

여유가 되면 붙인다. 없어도 실험은 성립하지만, 있으면 결론이 훨씬 단단해진다.

쿼리 세 개가 한 벌이다.

```cpp
ComPtr<ID3D11Query> m_disjoint;   // D3D11_QUERY_TIMESTAMP_DISJOINT
ComPtr<ID3D11Query> m_tsBegin;    // D3D11_QUERY_TIMESTAMP
ComPtr<ID3D11Query> m_tsEnd;      // D3D11_QUERY_TIMESTAMP
```

```cpp
// 그리기 전후로 감싼다
m_context->Begin(m_disjoint.Get());
m_context->End(m_tsBegin.Get());

//  ... 드로우 콜들 ...

m_context->End(m_tsEnd.Get());
m_context->End(m_disjoint.Get());
```

```cpp
// 결과는 나중에 (같은 프레임에 바로 읽으면 GPU를 기다리게 된다)
D3D11_QUERY_DATA_TIMESTAMP_DISJOINT dj{};
if (m_context->GetData(m_disjoint.Get(), &dj, sizeof(dj), 0) == S_OK && !dj.Disjoint)
{
    UINT64 begin = 0, end = 0;
    m_context->GetData(m_tsBegin.Get(), &begin, sizeof(begin), 0);
    m_context->GetData(m_tsEnd.Get(),   &end,   sizeof(end),   0);
    gpuMs = double(end - begin) / dj.Frequency * 1000.0;
}
```

**`Disjoint`가 true면 그 측정은 버린다.** GPU 클럭이 도중에 바뀌었다는 뜻이라
숫자를 믿을 수 없다. 전력 관리나 다른 프로그램의 GPU 사용 때문에 생긴다.

**결과를 바로 읽지 않는다.** `GetData`를 그 프레임에 부르면 GPU가 끝날 때까지 기다리게 되어
측정 행위가 성능을 바꾼다. 몇 프레임 뒤에 읽거나, `S_FALSE`면 넘어간다.

## 7. 실험 설계 — 여기서 신뢰도가 갈린다

### 조건을 고정한다

| 항목 | 이유 |
|---|---|
| **Release 빌드로 측정** | Debug는 최적화가 꺼져 있어 CPU 비용이 부풀려진다. **가장 흔한 실수** |
| **난수 시드 고정** | 매번 다른 배치면 비교가 안 된다 |
| **창 크기 고정** | 픽셀 수가 바뀌면 GPU 부하가 바뀐다 |
| **다른 프로그램 종료** | 브라우저·디스코드가 GPU를 쓰면 결과가 흔들린다 |
| **워밍업 후 측정** | 초반 프레임은 셰이더 컴파일·캐시 때문에 느리다. **앞 60프레임 버린다** |
| **같은 화면 결과 확인** | 두 방식이 다른 그림을 그리면 비교 자체가 무효 |

### 측정 구간

```
N = 100, 500, 1000, 2000, 5000, 10000, 20000
각 조건에서 300프레임 측정 (앞 60 버리고 240개 사용)
개별 / 인스턴싱 두 방식
```

**로그 스케일에 가깝게 N을 잡는다.** 100, 200, 300... 으로 잡으면 변화가 안 보인다.
차이가 갈리는 지점을 찾으려면 배수로 늘려야 한다.

### 결과 표

| N | 개별 (ms) | 인스턴싱 (ms) | 배율 | CPU 제출 (개별/인스턴싱) | GPU (개별/인스턴싱) |
|---|---|---|---|---|---|
| 100 | | | | | |
| 500 | | | | | |
| 1,000 | | | | | |
| 5,000 | | | | | |
| 10,000 | | | | | |

## 8. 결론을 어떻게 쓰나

**표만 있으면 절반이다.** 나머지 절반은 해석이다.

### 답해야 할 세 질문

**1. 몇 개부터 갈라지는가**
> "N=500까지는 차이가 5% 이내였고, N=2000부터 2배 이상 벌어졌다."

**2. 왜 하필 거기인가**
> "CPU 제출 시간이 프레임 예산을 넘기기 시작하는 지점과 일치했다.
> N=2000에서 개별 방식의 CPU 제출이 11ms로, 60fps 예산 16.6ms의 대부분을 먹었다."

**3. 예상과 달랐던 것은 무엇인가**
> "N=100에서는 인스턴싱이 오히려 근소하게 느렸다.
> 인스턴스 버퍼를 Map/Unmap하는 고정 비용이 드로우 콜 100번보다 컸던 것으로 보인다."

**세 번째가 제일 값어치 있다.** 예상대로만 나온 실험은 누구나 쓸 수 있지만,
어긋난 지점을 찾아 원인을 좁힌 기록은 그 사람이 실제로 측정했다는 증거다.

> MiniOscReceiver에서 **"저부하에서는 차이가 없다는 반대 결과를 먼저 얻었다"**고 쓴 그 대목이
> 포트폴리오에서 제일 강한 문장이었다. 같은 것을 여기서도 노린다.
> **결과가 예상과 다르면 그게 실패가 아니라 재료다.**

---

## 9. 흔한 함정

| 증상 | 원인 |
|---|---|
| 두 방식이 똑같이 나옴 | **VSync를 안 껐다** — 1순위 |
| 개별 방식이 비현실적으로 느림 | **Debug 빌드로 쟀다** |
| 매번 결과가 다름 | 난수 시드 미고정 / 다른 프로그램이 GPU 사용 |
| GPU 시간이 0 또는 이상함 | `Disjoint` 검사를 안 함 |
| 측정하니 오히려 느려짐 | `GetData`를 같은 프레임에 블로킹으로 읽음 |
| 첫 결과만 유독 느림 | 워밍업 구간을 안 버림 |
| 인스턴싱이 더 느림 | `WRITE_DISCARD` 누락 ([07장](07_배칭과_인스턴싱.md)) |

## 10. 확인 문제

1. `Draw()` 앞뒤로 시간을 재면 무엇이 측정되나? GPU 시간인가?
2. VSync를 켠 채로 성능을 재면 왜 안 되나?
3. 평균 프레임 시간이 같은 두 방식 중 하나가 게임에 못 쓸 수 있다. 무엇을 더 봐야 하나?
4. 타임스탬프 쿼리의 `Disjoint`가 true면 어떻게 해야 하나? 왜인가?
5. 프레임 16ms, CPU 제출 2ms, GPU 15ms가 나왔다. 무엇이 병목이고 무엇을 고쳐야 하나?

> 5번 답 — **GPU 바운드.** CPU는 2ms만에 명령을 다 넣고 놀고 있다.
> 여기서 드로우 콜을 줄여봐야 소용없다. 픽셀 셰이더를 단순화하거나,
> 오버드로우를 줄이거나, 해상도를 낮춰야 한다.
> **진단이 반대면 최적화가 전부 헛수고가 된다** — 이것이 6장부터 이어진 이 교재의 결론이다.
