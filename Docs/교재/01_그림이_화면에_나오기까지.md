# 01. 그림이 화면에 나오기까지

> 상태: 완료 · 갱신 2026-08-11 · 관련: [교재 목차](00_이_교재를_읽는_법.md), [2단계 작업일지](../작업일지/2026-08-11_2단계_파이프라인과_삼각형.md), [02. 좌표계](02_좌표계.md)
> 무엇: 렌더링 파이프라인 다섯 단계. 정점 세 개가 어떻게 수십만 개의 픽셀이 되는가.

**이 장이 전부의 뼈대다.** 여기만 잡으면 나머지 일곱 장은 이 그림의 어느 자리에 무엇을 끼우는지의 이야기다.

---

## 1. 왜 필요한가

버그 리포트는 이렇게 들어온다.

> "특정 각도에서만 캐릭터가 사라져요"
> "이 맵에서만 프레임이 반토막 나요"
> "그림자가 한 프레임 늦게 따라와요"

이걸 좁히려면 **어느 단계에서 틀어졌는지** 짚어야 한다.
정점이 잘못 들어간 건지, 변환이 틀린 건지, 컬링에 걸린 건지, 픽셀 셰이더가 무거운 건지.

파이프라인 그림이 없으면 이 질문 자체를 못 만든다.

---

## 2. 개념 — 다섯 단계

```
   정점 버퍼 (GPU 메모리에 올려둔 숫자 뭉치)
        │
   ┌────▼────────────────────────────────────────┐
   │ IA   Input Assembler                        │  고정
   │      바이트를 정점으로 조립하고 삼각형으로 묶음   │
   └────┬────────────────────────────────────────┘
        │  정점 3개
   ┌────▼────────────────────────────────────────┐
   │ VS   Vertex Shader                          │  ★ 우리가 코드를 씀
   │      정점 하나당 1번. 위치를 정한다             │
   └────┬────────────────────────────────────────┘
        │  화면 좌표를 가진 정점 3개
   ┌────▼────────────────────────────────────────┐
   │ RS   Rasterizer                             │  고정
   │      삼각형을 픽셀로 쪼갬 + 값을 보간           │
   │      + 화면 밖/뒷면 잘라내기                   │
   └────┬────────────────────────────────────────┘
        │  픽셀 수십만 개
   ┌────▼────────────────────────────────────────┐
   │ PS   Pixel Shader                           │  ★ 우리가 코드를 씀
   │      픽셀 하나당 1번. 색을 정한다               │
   └────┬────────────────────────────────────────┘
        │  색 수십만 개
   ┌────▼────────────────────────────────────────┐
   │ OM   Output Merger                          │  설정만 함
   │      기존 픽셀과 섞어서(블렌딩) 최종 기록        │
   └────┬────────────────────────────────────────┘
        │
    렌더 타깃 (백버퍼)
```

**우리가 코드를 쓰는 곳은 VS와 PS 둘뿐이다.** 나머지는 하드웨어가 정해진 대로 한다.
RS는 아예 못 건드리고, IA와 OM은 "이렇게 해라"고 설정만 한다.

### 각 단계 한 줄 요약

| 단계 | 입력 | 출력 | 우리가 하는 일 |
|---|---|---|---|
| **IA** | 바이트 뭉치 | 정점 | 해석 규칙(입력 레이아웃)을 준다 |
| **VS** | 정점 1개 | 화면 좌표를 가진 정점 1개 | **HLSL 코드를 쓴다** |
| **RS** | 삼각형 | 픽셀 조각들 | 없음 (상태만 설정) |
| **PS** | 픽셀 1개 | 색 1개 | **HLSL 코드를 쓴다** |
| **OM** | 색 | 렌더 타깃에 기록 | 블렌드/뎁스 상태를 설정 |

## 3. 실행 횟수가 성능의 전부다

```
삼각형 1개, 화면 절반을 덮는 경우

  VS  →  3번 실행
  PS  →  약 460,000번 실행   (1280 x 720의 절반)
```

**15만 배 차이다.**

그래서 렌더링 최적화의 제1원칙이 나온다.

> **같은 계산이면 최대한 정점 단계로 올린다.**

정점당 계산은 공짜에 가깝고, 픽셀당 계산은 비싸다.
"이 조명 계산을 버텍스에서 할까 픽셀에서 할까"가 실제로 오가는 대화다.

> **언리얼에서는** — 머티리얼 에디터의 `Vertex Interpolator` 노드가 정확히 이것이다.
> 픽셀에서 하던 계산을 정점으로 옮겨 비용을 낮추는 장치다.

---

## 4. 보간 — RS가 몰래 해주는 일

정점 3개에만 색을 넣었는데 삼각형 안쪽이 부드러운 그라데이션이 된다.
우리가 계산한 적이 없다.

**RS가 VS의 출력값을 픽셀 위치에 맞춰 자동으로 섞어준다.** 이것이 보간(interpolation)이다.

```
     빨강 (정점 A)
       /\
      /  \        ← 이 안의 모든 픽셀은
     /    \          A, B, C의 값이 거리에 비례해 섞인 값을 받는다
    /______\
 파랑      초록
 (C)        (B)
```

중요한 것은 **색만 그런 게 아니라는 점**이다.
VS에서 PS로 넘기는 **모든 값**이 이렇게 섞인다 — UV 좌표, 법선, 월드 위치 전부.

4장에서 텍스처를 붙일 때, 정점 4개에만 UV를 주는데 안쪽 픽셀이 알맞은 텍스처 위치를 받는 이유가 이것이다.

**예외가 하나 있다.** `SV_Position`은 특별 취급되고,
`nointerpolation` 키워드를 붙이면 보간을 끌 수도 있다(첫 정점 값을 그대로 씀).

## 5. `SV_` 접두사 — 약속된 이름

```hlsl
float4 position : SV_Position;   // "이게 최종 화면 좌표다"
float4 color    : COLOR;         // 아무 이름이나 가능
```

`SV_`는 **System Value**의 약자다. GPU가 특별하게 다루는 값이라는 표시.

| 이름 | 의미 |
|---|---|
| `SV_Position` | VS 출력에서: 최종 화면 좌표. **RS가 이걸 보고 삼각형을 쪼갠다. 필수** |
| `SV_Target` | PS 출력에서: 이 색을 렌더 타깃에 쓴다 |
| `SV_VertexID` | VS 입력에서: 몇 번째 정점인지 (버퍼 없이 그릴 때 쓴다) |
| `SV_InstanceID` | 몇 번째 인스턴스인지 — **7장 인스턴싱에서 쓴다** |

`SV_`가 없는 이름(`POSITION`, `COLOR`, `TEXCOORD`)은 그냥 꼬리표다.
**C++ 입력 레이아웃의 이름과 맞기만 하면 뭐든 된다.**

## 6. 코드로는 — 셋이 맞아야 한다

제일 헷갈리는 부분이자 제일 자주 깨지는 부분.

```
C++ 구조체              입력 레이아웃                     HLSL
─────────────          ────────────────                ──────────────────────────
struct Vertex {        { "POSITION", 0,                struct VSInput {
  float x, y;            R32G32_FLOAT, 0, 0, ... },      float2 position : POSITION;
  float r,g,b,a;       { "COLOR",    0,                  float4 color    : COLOR;
};                       R32G32B32A32_FLOAT, 0, 8, ...} };
```

**세 군데가 같은 것을 세 가지 방식으로 적은 것이다.**

- C++ 구조체 — 메모리에 어떻게 깔릴지
- 입력 레이아웃 — GPU에게 그 바이트를 어떻게 읽으라고
- HLSL — 셰이더가 그것을 어떤 이름으로 받을지

정점에 값을 하나 추가하면 **세 군데를 전부 고쳐야 한다.** 하나만 고치면 반드시 깨진다.

`CreateInputLayout`에 정점 셰이더 바이트코드를 같이 넘기는 이유가 여기 있다.
런타임이 그 자리에서 "레이아웃과 셰이더 입력이 맞는가"를 검증한다.

## 7. Draw는 개수만 넘긴다

```cpp
m_context->Draw(3, 0);   // 정점 3개를, 0번부터
```

**무엇을, 어디에, 어떤 셰이더로가 하나도 없다.**
D3D11이 상태 기반(state-based) API이기 때문이다. 그리기 전에 파이프라인 각 자리에 꽂아둔다.

```cpp
m_context->IASetInputLayout(...);        // IA 자리
m_context->IASetVertexBuffers(...);      // IA 자리
m_context->IASetPrimitiveTopology(...);  // IA 자리
m_context->VSSetShader(...);             // VS 자리
m_context->PSSetShader(...);             // PS 자리
m_context->OMSetRenderTargets(...);      // OM 자리
m_context->Draw(3, 0);                   // 그려
```

**함수 이름 앞 두 글자가 파이프라인 단계다.** `IASet`, `VSSet`, `PSSet`, `RSSet`, `OMSet`.
이걸 알면 처음 보는 함수도 어느 자리인지 바로 안다.

### 그래서 Clear는 되고 Draw는 안 된다

| 종류 | 방식 | 예 |
|---|---|---|
| **직접 지정형** | 대상을 인자로 받음. 파이프라인 무관 | `ClearRenderTargetView`, `Map`, `CopyResource` |
| **상태 의존형** | 미리 꽂아둔 것만 보고 동작 | `Draw`, `DrawIndexed`, `DrawInstanced` |

`OMSetRenderTargets`를 주석 처리해도 `Clear`는 멀쩡했던 이유다.
`Clear`는 뷰를 손가락으로 가리키고, `Draw`는 "그려"라고만 한다.

## 8. 엔진에서는

| 이 장의 개념 | 언리얼 | 유니티 |
|---|---|---|
| 정점 셰이더 | 머티리얼의 World Position Offset | Shader의 `vert` 함수 |
| 픽셀 셰이더 | 머티리얼의 Base Color 등 대부분 | `frag` 함수 |
| 입력 레이아웃 | Vertex Factory가 처리 | Mesh가 처리 |
| 백페이스 컬링 | 머티리얼의 Two Sided 체크박스 | `Cull Back/Front/Off` |
| Draw 호출 | `stat rhi`의 Draw Primitive calls | Profiler의 Draw Calls |

**엔진은 이 다섯 단계를 전부 자동으로 세팅한다.**
메시를 놓고 머티리얼을 붙이면 IA/VS/RS/PS/OM이 알아서 채워진다.
편한 대신, 뭔가 잘못됐을 때 어디를 봐야 할지 모르게 된다.

## 9. 흔한 함정

**정점 순서가 반시계 방향**
→ 백페이스 컬링으로 삼각형이 통째로 사라진다. **화면에 아무것도 없을 때 1순위 의심**.
D3D 기본은 시계 방향이 앞면이다.

**시맨틱 이름 오타**
→ `CreateInputLayout`이 실패한다. 다행히 실패가 눈에 보인다.

**`SV_Position`을 빼먹음**
→ RS가 어디에 그릴지 모른다. 셰이더 컴파일 단계에서 잡힌다.

**PS에서 알파를 0으로 반환**
→ 블렌딩이 켜져 있으면 완전히 투명해서 안 보인다. 블렌딩 끄면 보인다.
5장 이후에 자주 겪는다.

**좌표를 픽셀 값으로 넣음**
→ `(640, 360)` 같은 값은 NDC 범위 밖이라 화면에 안 보인다. 2장 주제.

## 10. 확인 문제

답할 수 있으면 다음 장으로.

1. 화면을 가득 채우는 삼각형 하나를 그릴 때 VS와 PS는 각각 몇 번쯤 실행되나?
2. 정점 3개에만 색을 줬는데 안쪽이 그라데이션인 이유는?
3. `Draw()`에 "어느 셰이더로 그릴지"가 안 들어가는데 GPU는 그걸 어떻게 아나?
4. 화면에 아무것도 안 나온다. 가장 먼저 의심할 세 가지는?
5. 무거운 계산을 픽셀 셰이더에서 정점 셰이더로 옮기면 왜 빨라지나? 항상 옮겨도 되나?

> 5번 보충 — 항상 되는 건 아니다. 정점 단위로 계산하면 값이 **보간**되므로
> 픽셀마다 정확히 계산한 것과 결과가 달라진다. 부드럽게 변하는 값은 옮겨도 되고,
> 급격히 변하는 값은 옮기면 눈에 띄게 뭉개진다.
> 정점이 픽셀보다 많은 극단적인 경우(아주 조밀한 메시)에는 오히려 손해다.
