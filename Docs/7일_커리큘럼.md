## 1일차 — 08-12 (수) · 렌더링 파이프라인과 삼각형

**오늘이 제일 큰 산이다.** 여기만 넘으면 나머지는 변주다.

### 개념 (1시간)

정점 세 개가 어떻게 화면의 픽셀이 되는가.

```
IA  Input Assembler   정점 버퍼에서 정점을 꺼내 조립한다
 ↓                    "이 바이트 뭉치는 이런 구조다"를 입력 레이아웃으로 알려줘야 한다
VS  Vertex Shader     정점 하나당 한 번 실행. 위치를 정한다
 ↓
RS  Rasterizer        삼각형을 픽셀 조각으로 쪼갠다  ← 고정 기능, 우리가 못 건드림
 ↓
PS  Pixel Shader      픽셀 하나당 한 번 실행. 색을 정한다
 ↓
OM  Output Merger     최종 색을 렌더 타깃에 쓴다
```

**꼭 잡을 것**
- VS는 정점당, PS는 픽셀당 실행된다. 삼각형 하나에 VS 3번, PS 수만 번.
- 입력 레이아웃이 왜 필요한가 — GPU는 정점 버퍼가 그냥 바이트 뭉치로 보인다.
  "앞 16바이트는 위치, 다음 8바이트는 UV"를 따로 알려줘야 한다.
- NDC(정규화 장치 좌표) — VS가 내놓는 좌표는 화면 픽셀이 아니라 **-1 ~ +1** 범위다.
  화면 중앙이 (0,0), 좌상단이 (-1, +1). 실제 픽셀 변환은 뷰포트가 한다.

**읽을 것**
- Microsoft Learn — "Graphics pipeline" (`direct3d11/overviews-direct3d-11-graphics-pipeline`)
- `Desktop/HGraphics/01_DX11InitAndImGui`의 `InitShaders()`와 `VS.hlsl` / `PS.hlsl`
  — 개념 확인용으로만 본다. 코드는 옮기지 않는다.

### 구현 (2~3시간)

1. `Vertex` 구조체 (위치 + 색)
2. 정점 버퍼 생성 — `D3D11_BUFFER_DESC`, `CreateBuffer`
3. `VS.hlsl` / `PS.hlsl` 작성
4. `D3DCompileFromFile`로 컴파일 → `CreateVertexShader` / `CreatePixelShader`
5. 입력 레이아웃 — `D3D11_INPUT_ELEMENT_DESC`, `CreateInputLayout`
6. `Render()`에 바인딩 후 `Draw(3, 0)`

### 오늘 끝난 기준

화면 가운데 **색이 있는 삼각형**이 뜬다.

### 오늘 반드시 해볼 실험

`OMSetRenderTargets`를 주석 처리한다. **이번엔 진짜로 깨진다.**
`Clear`는 되는데 `Draw`는 안 되는 이유를 눈으로 확인하는 순간이다.

## 2일차 — 08-13 (목) · 좌표계와 상수 버퍼

### 개념 (1시간)

- **인덱스 버퍼** — 사각형은 삼각형 2개. 정점 6개가 아니라 4개 + 인덱스 6개로 만든다. 왜 이득인가.
- **NDC ↔ 스크린 좌표** — "화면 (100, 50) 위치에 200×200 크기" 같은 말을 어떻게 -1~1로 바꾸는가.
- **상수 버퍼** — 셰이더에 매 프레임 값을 넘기는 통로. 정점 버퍼와 무엇이 다른가.
- **16바이트 정렬** — 상수 버퍼가 처음 사람을 무너뜨리는 지점.
  구조체 크기가 16의 배수가 아니면 값이 밀린다.

### 구현

1. 인덱스 버퍼로 사각형 (`DrawIndexed(6, 0, 0)`)
2. 상수 버퍼 구조체 — 화면 크기, 스프라이트 위치, 크기
3. `CreateBuffer`(`D3D11_BIND_CONSTANT_BUFFER`) → `VSSetConstantBuffers`
4. `Map` / `Unmap`으로 매 프레임 갱신
5. VS에서 스크린 좌표를 NDC로 변환

### 오늘 끝난 기준

**화면 아무 위치에, 원하는 크기로** 사각형이 뜬다. C++ 쪽 숫자만 바꿔서.

## 3일차 — 08-14 (금) · 텍스처와 샘플러

### 개념 (1시간)

- **UV 좌표** — 텍스처 안의 위치. 좌상단 (0,0), 우하단 (1,1). NDC와 y 방향이 반대다.
- **`ShaderResourceView`** — "이 텍스처를 읽는 재료로 쓴다"는 꼬리표. RTV와 짝.
- **샘플러** — 필터(`POINT`는 네모나게, `LINEAR`는 부드럽게)와 주소 모드(`WRAP`/`CLAMP`).
- **WIC** — Windows 내장 이미지 디코더. 외부 라이브러리 없이 PNG를 읽는다.

### 구현

1. WIC로 PNG → 픽셀 배열 (`IWICImagingFactory`, `CreateDecoderFromFilename`, `WICConvertBitmapSource`)
2. `CreateTexture2D` → `CreateShaderResourceView`
3. `CreateSamplerState`
4. `Vertex`에 UV 추가 → 입력 레이아웃도 같이 수정
5. PS에서 `Sample()`

### 오늘 끝난 기준

**그림이 붙은 스프라이트 한 장**이 뜬다.

> WIC 코드는 COM 초기화(`CoInitializeEx`)가 필요하고 장황하다.
> 여기서 2시간 넘게 막히면 넘어가고, 임시로 코드에서 만든 체커보드 텍스처를 쓴다.
> 텍스처를 **어디서 얻느냐**는 이 프로젝트의 본질이 아니다.

## 4일차 — 08-15 (토) · 블렌딩과 상태 객체 — *여유일*

### 개념 (1시간)

- **알파 블렌딩 수식** — `결과 = 새 색 × SrcAlpha + 기존 색 × (1 - SrcAlpha)`
- **왜 순서가 중요한가** — 블렌딩은 "기존 색"을 읽으므로 그리는 순서에 따라 결과가 다르다.
  불투명은 순서 무관, 투명은 뒤에서 앞으로 정렬해야 한다.
- **상태 객체를 미리 만드는 이유** — `ID3D11BlendState`는 만들 때 검증하고 GPU 상태로 굳힌다.
  매 프레임 설정값을 넘기지 않고 미리 만든 객체를 `Set`만 한다. 상태 변경이 비싸다는 것과 연결.

### 구현

1. `CreateBlendState` — `SRC_ALPHA` / `INV_SRC_ALPHA`
2. `OMSetBlendState`
3. 스프라이트 여러 장을 위치를 달리해 겹쳐 그리기

### 오늘 끝난 기준

투명 배경 PNG가 **네모 배경 없이** 제대로 나오고, 겹쳐도 자연스럽다.

**밀렸으면 오늘 따라잡는다.**

## 5일차 — 08-16 (일) · 드로우 콜 비용

### 개념 (1시간)

드로우 콜 하나에 무슨 비용이 드는가.

- CPU가 명령을 만들어 드라이버에 넘기는 비용 (검증, 커맨드 버퍼 기록)
- 상태 변경 비용 — 셰이더·텍스처·버퍼가 바뀌면 GPU가 파이프라인을 다시 세팅
- **GPU가 노는 시간** — 명령이 늦게 도착하면 GPU는 기다린다

여기서 "CPU 바운드"라는 말의 의미가 나온다. GPU는 여유로운데 CPU가 명령을 못 대주는 상태.

### 구현

1. 스프라이트 N개를 구조체 배열로 관리 (위치·크기·색)
2. `for` 루프 안에서 각각 상수 버퍼 갱신 → `DrawIndexed` — **N번 호출**
3. N을 코드 상수로 쉽게 바꿀 수 있게

### 오늘 끝난 기준

N = 1000 정도에서 스프라이트가 잔뜩 뜬다. **아직 느려도 된다. 느린 게 정상이다.**

## 6일차 — 08-17 (월) · 배칭과 인스턴싱

### 개념 (1시간)

같은 그림 N개를 한 번에 그리는 두 방법.

| 방법 | 하는 일 | 언제 |
|---|---|---|
| **동적 정점 버퍼 배칭** | N개의 정점을 CPU에서 큰 버퍼 하나에 모아 `DrawIndexed` 한 번 | 크기·회전이 제각각인 2D 스프라이트 |
| **인스턴싱** | 정점은 하나만 두고, 인스턴스별 데이터(위치 등)를 따로 넘겨 `DrawInstanced` | 같은 메시가 여러 개 |

- `D3D11_INPUT_PER_INSTANCE_DATA` — 입력 레이아웃에서 "이건 정점당이 아니라 인스턴스당"
- `D3D11_MAP_WRITE_DISCARD` — 매 프레임 버퍼를 통째로 새로 쓸 때. 왜 `NO_OVERWRITE`가 아닌가.

### 구현

둘 중 **인스턴싱 하나만** 한다 (시간이 남으면 배칭도).

1. 인스턴스 버퍼 (위치·크기·색)
2. 입력 레이아웃에 인스턴스 슬롯 추가
3. `IASetVertexBuffers`에 버퍼 2개
4. `DrawIndexedInstanced(6, N, 0, 0, 0)` — **한 번 호출**
5. 개별 방식과 스위치로 전환 가능하게 (`bool useInstancing`)

### 오늘 끝난 기준

**같은 화면이 두 방식으로 나오고, 전환할 수 있다.** 이게 내일 실험의 전제다.

## 7일차 — 08-18 (화) · 계측과 실험 — *이 프로젝트의 목적지*

### 개념 (1시간)

- **CPU/GPU 비동기** — `Draw()`는 명령을 큐에 넣을 뿐이다. `Present` 시점에도 GPU는 몇 프레임 뒤처져 있다.
- **타임스탬프 쿼리** — `D3D11_QUERY_TIMESTAMP` + `TIMESTAMP_DISJOINT`로 GPU 시간을 잰다.
- **VSync를 반드시 끈다** — `Present(0, 0)`. 안 끄면 전부 주사율에 고정돼 차이가 사라진다.
- **평균만 보지 않는다** — 최소·최대·중앙값도 본다. 평균이 같아도 튀는 정도가 다를 수 있다.

### 구현

1. `Present(0, 0)`으로 변경
2. `FrameTimer` 확장 — 프레임 시간 누적, 평균/최소/최대
3. GPU 타임스탬프 쿼리 (여유 있으면)
4. **N을 100 / 500 / 1000 / 5000 / 10000으로 바꿔가며 두 방식 측정**
5. 결과를 표로 기록

### 오늘 끝난 기준

이런 표가 나온다.

| N | 개별 드로우 콜 | 인스턴싱 | 차이 |
|---|---|---|---|
| 100 | ? ms | ? ms | |
| 500 | | | |
| 1,000 | | | |
| 5,000 | | | |
| 10,000 | | | |

**그리고 이 질문에 답을 쓴다 — "몇 개부터 갈라지는가. 왜 하필 거기인가."**

이게 포트폴리오의 핵심 한 줄이 되고, 면접에서 제일 많이 받을 질문이다.
저부하에서 차이가 없다면 그것도 그대로 쓴다. MiniOscReceiver 때와 같다.
