## 왜 하루를 여기에 썼나

2단계에서 새 개념이 다섯 개 한꺼번에 나왔다. 셰이더, 컴파일, 정점 버퍼, 입력 레이아웃, 드로우 콜.
읽어서 아는 것과 **결과를 미리 맞힐 수 있는 것은 다르다.**

그래서 3단계(좌표계·상수 버퍼)로 넘어가기 전에 하루를 잘라 썼다.
상수 버퍼는 삼각형 코드 위에 얹히는 것이라, 아래가 흐리면 위도 흐려진다.

**방식은 하나로 정했다 — 부수기 전에 결과를 글로 먼저 적는다.**
예측이 맞으면 이해한 것이고, 빗나가면 거기가 모르는 지점이다.
이 규칙 덕분에 아래 "막힌 것"에서 **코드 버그와 내 오해를 가를 수 있었다.** 그게 오늘의 수확이다.

- 삼각형 코드를 **여섯 가지로 부숴 확인.** 예측이 빗나간 곳은 두 군데
- **래스터라이저 상태(`ID3D11RasterizerState`)를 붙여** 컬링 규칙을 코드에서 제어

- D3D11 디버그 레이어 경고 두 종(#355, #356)을 실제로 띄우고 원문 해석

## 부순 것 여섯 가지

각각 예측을 먼저 적고, 하나만 고치고, 되돌렸다. **두 개를 동시에 고치면 원인을 못 가른다.**

| # | 고친 것 | 결과 | 확인한 것 |
|---|---|---|---|
| 1 | 정점 하나의 색 | 그 꼭짓점 주변부터 삼각형 안쪽까지 색이 번짐 | 보간은 래스터라이저가 한다 |
| 2 | 위 꼭짓점 `y: 0.5 → 2.0` | 윗변이 잘린 사다리꼴 | 클리핑 |
| 3 | 정점 순서를 반시계로 | **삼각형이 사라짐** | 백페이스 컬링 |
| 4 | `Draw(3,0) → Draw(2,0)` | 아무것도 안 나옴. **경고도 없음** | 불완전 프리미티브는 조용히 버려진다 |
| 5 | 토폴로지를 `LINESTRIP`으로 | 선 **2개**. 3→1이 안 닫힘 | 토폴로지는 해석 규칙일 뿐 |
| 6 | 입력 레이아웃 `COLOR` 오프셋 `8 → 12` | 색이 깨짐. **크래시는 없음** | 경고 #355 / #356 |

## 확인 문제 — 답하고 보완한 것

### 1. 2번 실습에서 GPU는 실제로 무엇을 했나

**내 답** — GPU가 첫 번째 정점을 화면 크기만큼 위로 보내버린 것 같다.

**보완** — GPU는 아무것도 옮기지 않았다. `y = 2.0`을 넣었으니 정점은 정확히 거기(화면 위 바깥)에 있다.
일어난 일은 **클리핑(clipping)** 이다. 래스터라이저 직전에 화면 밖으로 나간 부분을 잘라내고,
**화면 경계에 새 정점을 만들어 삼각형을 다시 구성한다.** 그래서 뾰족한 꼭짓점이 아니라 윗변이 평평한 사다리꼴이 나왔다.

"모양이 달라 보인" 것은 두 가지가 겹친 결과다.
밑변 두 점은 그대로인데 꼭짓점만 위로 갔으니 **옆변 기울기가 가팔라졌고**, 그 길어진 삼각형의 **아랫동강만 화면에 남았다.**

> 3D에서 "카메라 뒤에 있는 물체"를 처리하는 기계가 이것이다. 지금 2D에서 보는 게 그 전부다.

### 2. 반시계로 바꾸면 왜 사라지나. 그걸 끄려면 무엇을 건드리나

**내 답** — 뒷면을 그린다고 판단해서 버렸다. 끄는 것은 `FLIP_DISCARD`?

**보완** — 앞부분은 맞다. 정점 세 개를 읽은 순서가 반시계라 뒷면으로 판정하고 버렸다.
용어로는 **와인딩(winding order)** 과 **백페이스 컬링**. D3D 기본값이 `시계 = 앞면`, `뒷면은 버림`이다.

뒷부분은 틀렸다. **`FLIP_DISCARD`는 다 그린 화면을 모니터에 넘기는 방식**(스왑체인)이라 컬링과 무관하다.
이름에 DISCARD가 들어가 헷갈린 것.

정답은 **래스터라이저 상태(`ID3D11RasterizerState`)** 다. 아래 "래스터라이저 상태를 붙였다" 참고.

### 3. `LINESTRIP`에서 선이 몇 개인가. 왜 안 닫히나

**내 답** — 2개. 1→2→3은 이어지는데 3→1이 안 이어진다. 토폴로지 처리 방식 때문.

**보완** — 맞다. `LINESTRIP`은 순서대로 잇기만 하고 마지막과 처음을 안 닫는다. 정점 3개 → 선분 2개.
닫으려면 정점 4개(마지막에 첫 점을 한 번 더)를 넣거나 `LINELIST`로 6개를 넣는다.

덧붙일 것 — **정점 버퍼는 손대지 않았다.** 같은 바이트를 **몇 개씩 끊어 읽을지**만 바뀌었다.
4번 실습에서 아무것도 안 나온 이유도 같다. `TRIANGLELIST`는 3개씩 끊는데 2개면 완성이 안 돼 통째로 버린다.

```
Draw(3, 0)  →  [0 1 2]           삼각형 1개
Draw(2, 0)  →  [0 1 ?]           못 채움 → 버림. 0개
Draw(5, 0)  →  [0 1 2] [3 4 ?]   1개 + 버림
```

정수 나눗셈과 같다. `5 / 3 = 1`, 나머지는 버린다. 특별 취급도 예외도 없다.
**그래서 "출력할 게 없다고 판단했다"가 아니라, 래스터라이저까지 내려간 프리미티브가 하나도 없었다**가 정확하다.

### 4. 오프셋을 어긋냈는데 왜 크래시가 안 나나

**내 답** — 시맨틱 이름은 안 틀렸으니 GPU가 크래시 낼 이유가 없다.

**보완** — 그건 **`CreateInputLayout`이 통과한 이유**다. 검증은 이름과 포맷만 본다.
문제는 만들 때가 아니라 **읽을 때** 생긴다.

정점 하나는 24바이트(위치 8 + 색 16). 오프셋을 12로 하면 각 정점 자리에서 **12~27바이트**를 색으로 읽는다. 24를 넘는다.

```
정점0: [x y][r g b a] 정점1: [x y][r g b a] 정점2: [x y][r g b a]
바이트 0        8   23 24      32       47 48      56       71
             └12~27┘  ← 색으로 읽는 구간. 다음 정점의 x까지 먹는다
```

- 정점 0·1 → 옆 정점 데이터를 색으로 읽는다. 유효한 메모리라 아무 일도 안 난다
- 정점 2 → 버퍼 끝(72)을 넘는다. **D3D는 버퍼 범위 밖 읽기를 0으로 돌려주도록 정해져 있다**

그래서 진짜 답은 — **GPU 파이프라인에는 타입이 없다. 바이트와 해석 규칙만 있다.**
규칙이 틀려도 바이트는 여전히 읽히므로, 죽는 대신 **틀린 그림**이 나온다.

**이것이 그래픽 디버깅이 어려운 근본 이유다.** CPU 코드는 틀리면 죽어서 알려주는데, GPU 코드는 조용히 이상해진다.

> 정점 2는 알파까지 0이 됐는데 사라지지 않았다. **블렌딩이 꺼져 있어 알파를 아무도 안 본다.**
> 4일차에 블렌딩을 켜는 순간 이게 증상으로 튀어나올 자리다.

### 5. `Draw` 한 줄만으로는 왜 안 되나

**내 답** — `Draw`는 정점 개수만 넘기고, 무엇을 어디에 어떤 셰이더로 그릴지가 하나도 없다.

**보완** — 맞다. 용어를 붙이면 **파이프라인은 상태 기계**이고, `Draw`는 "지금 꽂혀 있는 상태로 그려"라는 뜻이다.

**이 문장이 5·6일차의 뿌리다.** 드로우 콜이 비싼 이유의 절반이 이 상태를 세팅하고 검증하는 비용이고,
배칭이란 결국 **상태가 같은 것끼리 묶어 이 세팅을 한 번만 하는 것**이다.

### 6. VS와 PS는 각각 몇 번 실행됐나

**내 답** — VS는 3번. PS는 모르겠다.

**보완** — 계산할 수 있다. 삼각형이 NDC로 x·y 각각 `-0.5 ~ 0.5`, 창은 1280×720.
NDC 1.0은 가로 640픽셀, 세로 360픽셀이다.

```
삼각형 면적 = 1/2 × 640 × 360 = 115,200 픽셀   (화면 921,600의 약 1/8)
```

**VS 3번 : PS 115,200번 — 약 3만 8천 배.**

여기서 실무 원칙이 나온다 — **할 수 있는 계산은 정점 셰이더로 밀어라.**
VS에서 계산해 넘기면 나머지는 래스터라이저가 보간해준다. 같은 걸 PS에서 하면 3만 8천 번 한다.

> 실제로는 더 돈다. 픽셀 셰이더는 **2×2 묶음 단위**로 실행돼서 삼각형 가장자리에서는
> 바깥 픽셀까지 같이 실행됐다가 버려진다. **작은 삼각형이 비효율적이라는 말**이 여기서 나온다.

### 덤 — `Draw(2, 0)`에서 디버그 레이어가 조용했다

출력 창에 D3D 메시지가 하나도 없었다. 그런데 삼각형은 안 나왔다.
`Draw(2, 0)`은 **완벽하게 합법인 호출**이라 경고할 것이 없다.

> **디버그 레이어가 조용하다고 코드가 맞다는 뜻이 아니다.**
> 레이어는 "API를 잘못 썼는가"만 본다. "의도한 그림이 나오는가"는 안 본다.

교재 00장 디버깅 순서에서 1번(출력 창)이 조용하면 2~7번으로 내려가는 이유가 이것이다.

## 막힌 것 — `CULL_NONE`인데 삼각형이 안 나온다

오늘 제일 오래 붙잡은 곳이고, **예측을 먼저 적어둔 덕에 풀린 건**이다.

### 무엇을 하려 했나

2번 문제의 "끄는 방법"을 직접 만들어보려고 래스터라이저 상태를 붙였다.
확인표를 만들고 **세 줄의 결과를 미리 예측해 적었다.**

| 정점 순서 | `CullMode` | `FrontCounterClockwise` | 예측 | 실제 |
|---|---|---|---|---|
| 반시계 | `BACK` | `FALSE` | 안 보임 | 안 보임 |
| 반시계 | `NONE` | `FALSE` | **보임** | **안 보임** ← |
| 반시계 | `BACK` | `TRUE` | 보임 | **안 보임** ← |
| 시계 | `BACK` | `TRUE` | 안 보임 | **보임** ← |

### 어떻게 좁혔나

처음엔 "`CULL_NONE`이 내가 아는 것과 다른가?" 하고 개념을 의심했다. 그러다 표를 세로로 봤다.

**결과가 오로지 정점 순서로만 갈리고 있다.** `CullMode`를 바꾸든 `FrontCounterClockwise`를 뒤집든 아무 영향이 없다.
게다가 네 줄 전부가 **D3D 기본값(`CULL_BACK` / `FrontCCW=FALSE`)일 때 나올 결과와 정확히 일치**했다.

여기서 의심이 개념에서 코드로 넘어갔다 — **내가 적은 값이 애초에 적용되고 있지 않다.**

### 원인

`D3D11_RASTERIZER_DESC`를 채워놓고 **`CreateRasterizerState`를 부르지 않았다.**

```cpp
D3D11_RASTERIZER_DESC rd{};
rd.FillMode = D3D11_FILL_SOLID;
rd.CullMode = D3D11_CULL_NONE;
rd.FrontCounterClockwise = FALSE;
// ← CreateRasterizerState가 없다. rd는 그냥 스택 위의 C++ 구조체로 끝났다

return true;
```

`m_rasterizerState`는 비어 있었고, 매 프레임 이렇게 돌고 있었다.

```cpp
m_context->RSSetState(m_rasterizerState.Get());   // nullptr을 넘기는 중
```

**`RSSetState(nullptr)`은 에러가 아니라 "기본 상태로 되돌려라"는 유효한 명령이다.**
그래서 무엇을 적든 매 프레임 기본값으로 리셋됐고, 디버그 레이어도 조용했다. 합법적인 호출이니까.

### 여기서 얻은 것

**모든 D3D 객체가 같은 3단계다. 예외가 없다.**

```
1. DESC 구조체를 채운다     ← 그냥 C++ 값. 아무 일도 안 일어남
2. Create○○○ 로 넘긴다      ← 여기서 검증하고 진짜 GPU 객체가 됨
3. ○○Set○○○ 로 꽂는다       ← 이제부터 적용
```

| | 1. DESC | 2. Create | 3. Set |
|---|---|---|---|
| 정점 버퍼 | `D3D11_BUFFER_DESC` | `CreateBuffer` | `IASetVertexBuffers` |
| 입력 레이아웃 | `D3D11_INPUT_ELEMENT_DESC` | `CreateInputLayout` | `IASetInputLayout` |
| 스왑체인 | `DXGI_SWAP_CHAIN_DESC1` | `CreateSwapChainForHwnd` | — |
| 래스터라이저 | `D3D11_RASTERIZER_DESC` | `CreateRasterizerState` ← **빠뜨린 자리** | `RSSetState` |
| 샘플러 (3일차) | `D3D11_SAMPLER_DESC` | `CreateSamplerState` | `PSSetSamplers` |
| 블렌드 (4일차) | `D3D11_BLEND_DESC` | `CreateBlendState` | `OMSetBlendState` |

**2단계에서 검증이 일어난다**는 것이 요점이다. 만들 때 한 번 확인하고 GPU가 쓰는 형태로 굳혀두기 때문에,
매 프레임 `Set`은 싸고 `Create`는 초기화 때 몰아서 한다. 5일차 "상태 객체를 왜 미리 만드나"가 이 이야기다.

그리고 일반화 한 줄.

> **`Set` 계열은 `nullptr`을 받으면 조용히 기본값으로 돌아간다. 에러가 아니다.**
> 상태를 바꿨는데 화면이 안 변하면, 개념을 의심하기 전에 **그 객체가 진짜 만들어졌는지부터** 본다.
> `RSSetState` 줄에 중단점을 걸고 포인터가 null인지 보면 30초에 끝난다.

**예측을 먼저 적어두지 않았다면 "아, `CULL_NONE`이 이런 거구나" 하고 틀린 것을 배웠을 것이다.**
예측과 실제가 어긋난 게 아니라 **예측이 맞고 코드가 틀린** 경우였다. 이 둘을 가르려면 예측이 글로 남아 있어야 한다.

## 래스터라이저 상태를 붙였다

세 군데를 고쳤다.

**① 멤버 (`src/Renderer.h`)**

```cpp
ComPtr<ID3D11RasterizerState> m_rasterizerState;
```

**② 만들기 (`CreateTriangleResources()` 끝)**

```cpp
D3D11_RASTERIZER_DESC rd{};
rd.FillMode              = D3D11_FILL_SOLID;   // WIREFRAME으로 바꾸면 선만 그린다
rd.CullMode              = D3D11_CULL_BACK;    // NONE = 양면 다 그림
rd.FrontCounterClockwise = FALSE;              // TRUE면 반시계를 앞면으로 뒤집는다

if (!HR_CHECK(m_device->CreateRasterizerState(&rd, m_rasterizerState.GetAddressOf()),
              L"CreateRasterizerState"))
    return false;
```

**③ 꽂기 (`Render()`)**

```cpp
m_context->RSSetState(m_rasterizerState.Get());
```

### 고친 뒤 다시 돌린 확인표

| 정점 순서 | `CullMode` | `FrontCounterClockwise` | 보이나 |
|---|---|---|---|
| 반시계 | `BACK` | `FALSE` | 안 보임 |
| 반시계 | `NONE` | `FALSE` | **보임** |
| 반시계 | `BACK` | `TRUE` | **보임** |
| 시계 | `BACK` | `FALSE` | **보임** (기본 상태) |

**2행과 3행은 결과가 같지만 하는 일이 전혀 다르다.**

- `CULL_NONE` — **검사 자체를 끈다.** 앞뒤 구분 없이 다 그린다. 2D 스프라이트나 양면 판때기에 쓴다
- `FrontCounterClockwise = TRUE` — **앞뒤 기준을 뒤집는다.** 검사는 여전히 돈다.
  좌표계 손잡이(handedness)가 다른 툴에서 가져온 메시가 죄다 뒤집혀 나올 때 쓰는 스위치다

3번 실습만 봐서는 이 둘이 같아 보인다. 표로 갈라놓아야 구분된다.

> 커밋은 기본 상태(`CULL_BACK` / `FALSE` / 정점 시계 방향)로 되돌려서 했다.

|---|---|---|

| **와인딩** | 정점을 읽은 순서가 시계냐 반시계냐. 앞뒤를 이걸로 판정한다 | 실습 3 |
| **백페이스 컬링** | 뒷면 삼각형을 래스터라이즈 전에 버린다. 기본은 켜져 있다 | 실습 3 |
| **토폴로지** | 정점 몇 개씩 끊어 무엇으로 볼지. 버퍼가 아니라 **해석**을 바꾼다 | 실습 4·5 |
| **입력 레이아웃** | 바이트 뭉치의 해석 규칙. 오프셋이 틀려도 크래시는 안 난다 | 실습 6 |

| **상태 객체 3단계** | DESC 채우기 → `Create` → `Set`. 가운데가 빠지면 조용히 기본값 | 막힌 것 |

**`SV_` 안 붙은 값은 전부 보간을 타고 픽셀 셰이더로 간다.**
색뿐 아니라 UV, 법선도 마찬가지다. 3일차에 텍스처를 붙일 때 UV가 이 길로 넘어간다.

## 참고

- **D3D11 디버그 레이어 경고 원문** — 실습 6에서 실제로 받은 것

  ```
  #355: Input vertex slot 0 has stride 24 which is less than the minimum stride
        logically expected from the current Input Layout (28 bytes).
  #356: Vertex Buffer at the input vertex slot 0 is not big enough ...
        reading off the end of the Buffer is defined to return 0.
  ```

  둘 다 `This is OK, ... However the developer probably did not intend to make use of this behavior.`로 끝난다.
  **D3D 경고문의 성격이 여기 다 들어 있다** — 죽여야 할 만큼 틀린 게 아니면 안 죽이고, 대신 사람 말로 알려준다.
  `28`은 오프셋 12 + 색 16이다. 경고문이 계산해서 알려준 셈이라, 원인을 코드에서 찾기 전에 숫자로 확인됐다.

- Microsoft Learn — `D3D11_RASTERIZER_DESC`, `ID3D11Device::CreateRasterizerState`, `RSSetState`
  → `CullMode`와 `FrontCounterClockwise`가 별개 스위치라는 것을 여기서 확인
- Microsoft Learn — `D3D11_PRIMITIVE_TOPOLOGY`
  → `LINESTRIP`이 마지막-처음을 안 닫는다는 것
