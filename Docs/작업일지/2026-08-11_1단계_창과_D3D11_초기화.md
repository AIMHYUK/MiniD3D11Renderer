# 1단계 — Win32 창과 D3D11 초기화

> 상태: 완료 · 갱신 2026-08-11 · 관련: [작업일지 목차](../_목차.md), [스왑체인과 플립 모델](../개념/스왑체인과_플립모델.md)
> 무엇: 엔진 없이 창을 띄우고 Direct3D 11 디바이스·스왑체인·백버퍼 뷰를 만들어, 화면이 한 가지 색으로 지워지는 데까지.

---

## 결과

`1280 x 720` 창이 뜨고, 짙은 남색으로 지워지며, 제목 표시줄에 `144.0 FPS`가 갱신된다.
ESC 또는 닫기 버튼으로 정상 종료. 창 크기를 드래그로 바꿔도 깨지지 않는다.

```
MiniD3D11Renderer  |  1280 x 720  |  144.0 FPS
```

> 144 FPS는 성능이 아니라 **모니터 주사율**이다. `Present(1, 0)`으로 수직동기를 켜 뒀기
> 때문에 GPU가 얼마나 여유로운지와 무관하게 144에 붙는다. 4단계에서 드로우 콜 비용을
> 잴 때는 반드시 `Present(0, 0)`으로 바꿔야 한다. 안 그러면 모든 실험이 144로 똑같이 나온다.

---

## 왜 언리얼로 안 했는가

이 프로젝트의 목적이 "DirectX를 다룰 수 있다"를 보이는 것이기 때문이다.

언리얼은 RHI(Render Hardware Interface) 계층 뒤로 D3D11/D3D12/Vulkan을 감춘다.
언리얼로 아무리 잘 만들어도 내가 만진 것은 언리얼의 API지 DirectX가 아니다.
게다가 아키텍처를 설명하라는 요구에 대해, 언리얼 위에서는 설명할 아키텍처가 에픽의 것이 된다.

- 네오플 자격요건 — "DirectX를 활용한 2D/3D 게임 프로그래밍 및 응용 능력"
- 네오플 제출요건 — "렌더링 기능이 포함된 C++ 기반의 프로그램(실행 파일 및 소스 코드)",
  "아키텍처, 핵심 로직 및 코드 구조가 상세히 기술된 설명"
- 스마일게이트 6098 자격요건 — "Windows 시스템 프로그래밍 기본 지식", "3D그래픽스 및 DirectX 기본 지식"

그리고 언리얼 포트폴리오는 이미 6개 있다. 7번째를 더해서 얻는 것이 없다.

## 한 일

### 1. 구조를 두 덩어리로 갈랐다

```
Window     Win32 창 하나. D3D를 전혀 모른다.
Renderer   디바이스·스왑체인·백버퍼 뷰를 소유하고 한 프레임을 그린다.
main       둘을 연결하고 게임 루프를 돌린다.
```

`Window`가 `Renderer`를 직접 들고 있으면 편하지만 그렇게 하지 않았다.
창 크기가 바뀌었다는 사실만 `std::function` 콜백으로 알리고, 그것으로 무엇을 할지는
`main`이 정한다.

```cpp
window.SetResizeCallback([&renderer](UINT w, UINT h) {
    renderer.Resize(w, h);
});
```

이렇게 두면 `Window`는 나중에 다른 렌더러를 붙이든 아무것도 안 붙이든 그대로 쓸 수 있고,
의존이 한 방향으로만 흐른다. 배달왕에서 `IInventoryInputProvider`로 입력 종류를 숨겼던 것과
같은 이유다 — **아래쪽이 위쪽을 알지 않게 한다.**

### 2. 창 만들기에서 걸린 것들

**클라이언트 크기 보정.** `CreateWindowEx`에 넘기는 크기는 테두리와 제목 표시줄을 포함한
바깥 크기다. 그림이 그려지는 건 안쪽(클라이언트 영역)이다. 그냥 1280×720을 넘기면
실제 렌더 타깃은 1264×681 같은 값이 된다. `AdjustWindowRect`로 테두리 두께만큼 부풀린
값을 넘겨야 한다.

```cpp
RECT rect{ 0, 0, (LONG)width, (LONG)height };
AdjustWindowRect(&rect, style, FALSE);   // rect가 바깥 크기로 바뀐다
```

**WndProc은 C 함수 포인터다.** 멤버 함수를 등록할 수 없다. 그래서 `static` 함수로 한 번 받고,
창을 만들 때 `this`를 `HWND`에 붙여둔 다음 꺼내 쓴다.

```cpp
// CreateWindowEx의 마지막 인자로 넘긴 this가
// WM_NCCREATE에서 CREATESTRUCTW::lpCreateParams로 돌아온다
if (msg == WM_NCCREATE) {
    auto* self = (Window*)((CREATESTRUCTW*)lParam)->lpCreateParams;
    SetWindowLongPtrW(hwnd, GWLP_USERDATA, (LONG_PTR)self);
}
```

전역 변수를 쓰면 창이 하나일 때는 돌아가지만 둘이 되는 순간 무너진다.
`GWLP_USERDATA`는 창마다 하나씩 있는 저장 공간이라 그 문제가 없다.

**`hbrBackground = nullptr`.** 배경 브러시를 두면 GDI가 흰색으로 먼저 칠하고 그 위에
D3D가 그린다. 창 크기를 바꿀 때 흰색이 번쩍인다.

**`PeekMessage`지 `GetMessage`가 아니다.** 이 차이가 문서 편집기와 렌더러를 가른다.

| | 동작 | 맞는 프로그램 |
|---|---|---|
| `GetMessage` | 메시지가 올 때까지 스레드를 **재운다** | 입력이 있을 때만 다시 그리면 되는 것 (메모장) |
| `PeekMessage` | 큐가 비면 **곧바로 반환** | 입력이 없어도 계속 그려야 하는 것 (게임) |

`GetMessage`로 짜면 마우스를 안 움직이는 동안 화면이 멈춘다.

### 3. D3D11 초기화 — 왜 두 단계로 나눴는가

`D3D11CreateDeviceAndSwapChain`이라는 한 방에 끝내주는 함수가 있는데 쓰지 않았다.
**그 함수는 옛 방식(BitBlt 모델) 스왑체인만 만들기 때문이다.**

플립 모델을 쓰려면 디바이스를 먼저 만들고, DXGI 팩토리를 구해서 스왑체인을 따로 만들어야 한다.
팩토리는 아무거나 쓰면 안 되고 **이 디바이스를 만든 바로 그 어댑터의 것**이어야 한다.
그래서 이렇게 거슬러 올라간다.

```
ID3D11Device → IDXGIDevice → IDXGIAdapter → IDXGIFactory2
              (QueryInterface)  (GetAdapter)   (GetParent)
```

COM 객체가 서로 다른 인터페이스로 같은 실체를 가리키는 구조라 가능한 일이다.
`QueryInterface`는 "너 이 인터페이스도 되니?"라고 묻는 것이고, ComPtr의 `As()`가 그걸 감싼다.

자세한 내용은 → [스왑체인과 플립 모델](../개념/스왑체인과_플립모델.md)

### 4. 크기 변경 처리

`ResizeBuffers`는 **백버퍼를 참조하는 것이 하나라도 남아 있으면 실패한다.**
뷰를 `Reset()` 하는 것만으로는 부족하고, 디바이스 컨텍스트에 바인딩된 상태도 풀어야 한다.

```cpp
m_backBufferView.Reset();
m_context->OMSetRenderTargets(0, nullptr, nullptr);  // 바인딩 해제
m_context->Flush();                                   // 지연된 참조까지 비움
```

그리고 드래그로 크기를 바꾸는 동안 `WM_SIZE`가 수십 번 날아온다. 그때마다 스왑체인을
다시 만들면 낭비다. `WM_ENTERSIZEMOVE` / `WM_EXITSIZEMOVE`로 드래그 구간을 감싸고,
놓는 순간 한 번만 알리게 했다.

최소화하면 `0 x 0`이 온다. 크기 0인 스왑체인은 만들 수 없으므로 걸러야 한다.

## 막힌 것 — C4819와 C2660

첫 빌드가 이렇게 실패했다.

```
warning C4819: 현재 코드 페이지(949)에서 표시할 수 없는 문자가 파일에 들어 있습니다.
error C2660: 'D3D11CreateDevice': 함수는 9개의 인수를 사용하지 않습니다.
```

인자를 열 개 넘겼는데 아홉 개라고 한다. 인자 개수를 아무리 세어봐도 맞았다.

**원인은 인자가 아니라 인코딩이었다.** 소스 파일은 UTF-8인데 MSVC가 시스템 코드 페이지
(한국어 Windows = CP949)로 읽었다. CP949는 2바이트 문자 인코딩이라, UTF-8 한글의 어떤
바이트를 선행 바이트로 잘못 보면 **바로 뒤에 오는 바이트를 삼켜버린다.** 그렇게 주석 끝의
줄바꿈이 먹히면 다음 줄 코드가 주석 안으로 빨려 들어간다. 인자 하나가 사라진 이유가 그것이다.

즉 **C2660은 증상이고, C4819가 원인이었다.** 컴파일러가 알려준 진짜 정보는 경고 쪽에 있었다.

해결은 컴파일러에 "이 소스는 UTF-8이다"라고 알려주는 것.

```xml
<AdditionalOptions>/utf-8 %(AdditionalOptions)</AdditionalOptions>
```

BOM을 붙이는 방법도 있지만, `/utf-8`이 프로젝트 설정 한 줄로 끝나고 파일을 건드리지 않는다.

> 배운 것: 에러 메시지가 말이 안 될 때는 그 위의 경고를 먼저 본다.
> 특히 한글 주석 + MSVC 조합에서는 인코딩을 의심한다.

## 처음부터 계측을 넣은 이유

`FrameTimer`를 1단계부터 넣었다. 지금은 창 제목에 FPS를 띄우는 것뿐이라 없어도 된다.

그래도 넣은 건 이 프로젝트의 목적이 "스프라이트를 그린다"가 아니라
**"드로우 콜 방식에 따라 성능이 어떻게 갈라지는지를 실측한다"**이기 때문이다.
계측을 나중에 붙이면 그때 가서 구조를 뜯어야 한다.

`QueryPerformanceCounter`를 쓴다. `GetTickCount`는 해상도가 10~16ms라 프레임 단위를 못 잰다.
주파수(`QueryPerformanceFrequency`)는 부팅 후 바뀌지 않으므로 한 번만 받아 둔다.

순간 프레임 시간이 아니라 **1초 평균**을 쓴다. 순간값은 심하게 튀어서 두 방식을 비교할 수 없다.
