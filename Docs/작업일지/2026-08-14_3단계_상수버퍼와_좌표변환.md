## 결과

- **정점 4개 + 인덱스 6개**로 사각형. `Draw` → `DrawIndexed`
- **상수 버퍼 32바이트**가 매 프레임 CPU에서 GPU로 건너간다
- **C++ 숫자만 바꿔서** 화면 아무 위치에 원하는 크기로 사각형이 뜬다
- 정점을 NDC가 아니라 **`0~1` 단위 사각형**으로 바꿨다. 7단계 인스턴싱의 전제
- 오류 네 건. **그중 하나는 코드가 아니라 빌드 파이프라인 문제였다**

커밋을 셋으로 나눴다. 기능 변경과 이름 변경을 한 커밋에 섞지 않았다.

## 어떻게 했나

### ① 인덱스 버퍼 — 사각형

```cpp
const Vertex vertices[] = {          //   0 ────── 1
    { -0.5f,  0.5f, ... },  // 0 좌상 //   │ ╲      │
    {  0.5f,  0.5f, ... },  // 1 우상 //   │   ╲    │
    {  0.5f, -0.5f, ... },  // 2 우하 //   3 ────── 2
    { -0.5f, -0.5f, ... },  // 3 좌하
};
const uint16_t indices[] = { 0,1,2,  0,2,3 };
```

만드는 절차는 정점 버퍼와 **완전히 같다.** DESC → `Create` → `Set`. `BindFlags`만 다르다.

**꽂는 방식은 다르다.** 이 차이에 이유가 있다.

```cpp
IASetVertexBuffers(0, 1, m_vertexBuffer.GetAddressOf(), &stride, &offset);  // 배열
IASetIndexBuffer  (m_indexBuffer.Get(), DXGI_FORMAT_R16_UINT, 0);           // 하나
```

**정점 버퍼는 슬롯 여러 개에 꽂을 수 있고, 인덱스 버퍼는 파이프라인에 하나뿐이다.**
함수 이름의 복수형/단수형이 이미 그걸 말하고 있었다.
7단계에서 슬롯 0에 정점, 슬롯 1에 인스턴스 데이터를 꽂을 때 이 구조가 쓰인다.

### ② 상수 버퍼 — 32바이트

`float2` 세 개는 24바이트인데 **16의 배수여야 해서** 끝에 8바이트 패딩을 붙였다.

```cpp
struct SpriteConstants
{
    float screenWidth, screenHeight;   //  0 ~  7
    float posX, posY;                  //  8 ~ 15
    float sizeX, sizeY;                // 16 ~ 23
    float padding[2];                  // 24 ~ 31
};
static_assert(sizeof(SpriteConstants) % 16 == 0, "상수 버퍼는 16바이트 배수여야 한다");
```

`static_assert`를 건 이유는 **컴파일 시점에 걸리게 하기 위해서**다. 나중에 멤버를 추가할 때 화면이 깨지고 나서 찾는 것보다 낫다.

**규칙이 하나가 아니라 둘이라는 것을 확인했다.**

| | 규칙 | 어길 때 |
|---|---|---|
| A | 버퍼 **전체 크기**가 16의 배수 | `CreateBuffer` 실패. 시끄럽게 죽는다 |
| B | **변수 하나가** 16바이트 경계를 걸치면 안 된다 | **아무도 안 잡아준다.** 값만 밀린다 |

지금 배치는 B도 통과한다. `float2`끼리 짝지으면 8+8=16으로 맞아떨어져서 아무도 경계를 안 걸친다. 운이 아니라 구조 때문이다.

**끝에 패딩을 붙이는 게 항상 답은 아니다.** `float2` 다음에 `float4`가 오면 `float4`가 16 경계를 걸쳐 밀려나는데, 그때 필요한 패딩은 끝이 아니라 **중간**이다. 끝을 채우는 건 A를 위해서고, 중간을 채우는 건 B를 위해서다.

### ③ 만드는 자리와 채우는 자리가 다르다

여기서 정점 버퍼와 갈린다.

| | 그릇 만들기 | 내용물 넣기 |
|---|---|---|
| 정점/인덱스 버퍼 | `Create`에서 | **`Create`에서 같이** (`SUBRESOURCE_DATA`) |
| 상수 버퍼 | `Create`에서 | **`Render`에서 매 프레임** (`Map`) |

이 차이가 곧 `IMMUTABLE` vs `DYNAMIC`이다. 이름이 그대로 말한다 — 안 변할 것은 만들 때 넣고 봉인, 변할 것은 CPU가 쓸 수 있게 열어둔다. `CPUAccessFlags = D3D11_CPU_ACCESS_WRITE`를 **만들 때** 선언해야 하고 나중엔 못 바꾼다.

```cpp
// Render() 안. 지역 변수다. 이번 프레임에 보낼 32바이트를 조립하는 작업대일 뿐이라
// memcpy가 끝나면 죽어도 된다.
SpriteConstants constants{};
constants.screenWidth = static_cast<float>(m_width);
/* ... */

D3D11_MAPPED_SUBRESOURCE mapped{};
if (SUCCEEDED(m_context->Map(m_constantBuffer.Get(), 0, D3D11_MAP_WRITE_DISCARD, 0, &mapped)))
{
    memcpy(mapped.pData, &constants, sizeof(constants));
    m_context->Unmap(m_constantBuffer.Get(), 0);
}
m_context->VSSetConstantBuffers(0, 1, m_constantBuffer.GetAddressOf());
```

`Map`을 `SUCCEEDED`로 감쌌다. 실패하면 `mapped.pData`가 `nullptr`이고 거기에 32바이트를 쓰면 진짜로 죽는다. 매 프레임 도는 코드라 `HR_CHECK`(메시지 박스)는 못 쓴다 — 실패하면 창이 무한히 뜬다.

`WRITE_DISCARD`는 **기존 내용을 버리고 새 메모리를 준다.** 그래서 매번 구조체 전체를 써야 한다. 일부만 갱신하면 나머지가 쓰레기다. 대신 CPU가 GPU를 안 기다린다.

### ④ 좌표 변환

정점을 `-0.5~0.5`(NDC)에서 **`0~1` 단위 사각형**으로 바꿨다. 이제 이 값은 좌표가 아니라 **스프라이트 안에서의 비율**이다.

```hlsl
float2 screenPos = spritePos + input.position * spriteSize;   // ① 비율 → 픽셀
float2 ndc       = screenPos / screenSize;                    // ② 픽셀 → 0~1

ndc.x = ndc.x * 2.0f - 1.0f;    // ③ 0~1 → -1~+1
ndc.y = 1.0f - ndc.y * 2.0f;    //    y만 뒤집는다

output.position = float4(ndc, 0.0f, 1.0f);
```

`ndc.x = ...` 처럼 **성분 하나에만 대입할 수 있다.** x와 y는 공식이 달라서, `float2` 두 개를 만들어 합치는 것보다 이쪽이 짧다.

`w`에 `1.0f`를 넣는 이유 — 래스터라이저가 `SV_Position`을 `w`로 나눈다(원근 나눗셈). `0`을 넣으면 0으로 나눠서 좌표가 NaN이 되고 **삼각형이 통째로 버려진다.** 2D라 원근이 필요 없으니 1로 나눠 그대로 통과시키는 것.

## 막힌 것

### 1. 인덱스 버퍼가 정점 버퍼를 **대체**하는 줄 알았다

오늘 제일 크게 헛짚은 곳이다. 세 가지를 한꺼번에 틀렸다.

- 정점 버퍼의 `BindFlags`를 `INDEX_BUFFER`로 **바꿔버렸다**
- 인덱스 버퍼를 **아예 안 만들었다.** `m_indexBuffer`는 선언만 되고 `nullptr`
- `IASetVertexBuffers`를 **주석 처리했다**

당연히 화면이 비었다. IA에 꽂힌 게 아무것도 없었으니까.

**둘은 같이 있어야 한다.**

```
정점 버퍼   [v0][v1][v2][v3]        ← 실제 데이터
인덱스 버퍼 [0][1][2][0][2][3]       ← 저 버퍼의 몇 번을 어떤 순서로
```

**인덱스 버퍼에는 좌표가 없다. 번호만 있다.** 번호가 가리킬 대상이 없으면 아무 의미가 없다.

> **여기서 진짜 반성할 것은 출력 창을 안 본 것이다.**
> 디버그 레이어가 `DEVICE_DRAW_INDEX_BUFFER_NOT_SET`, `DEVICE_DRAW_VERTEX_BUFFER_NOT_SET`을
> 띄우고 있었을 것이다. 어제 "레이어가 조용하다고 코드가 맞다는 뜻이 아니다"를 배웠는데,
> **반대로 레이어가 말해줄 때 안 듣는 실수**를 오늘 했다.

### 2. `Get()` / `GetAddressOf()` — 양방향으로 다 틀렸다

같은 날 정반대로 두 번 틀렸다.

```cpp
IASetIndexBuffer(m_indexBuffer.GetAddressOf(), ...)          // ← Get()이어야 함
CreateBuffer(&desc, &data, m_indexBuffer.Get())              // ← GetAddressOf()여야 함
```

`GetAddressOf()`가 **두 가지 전혀 다른 이유로** 나와서 헷갈렸던 것이다.

| 호출 | 인자 선언 | 왜 `**`인가 |
|---|---|---|
| `CreateBuffer(..., pp)` | `ID3D11Buffer **ppBuffer` | **출력.** 함수가 여기에 써넣는다 |
| `IASetVertexBuffers(0,1,pp,...)` | `ID3D11Buffer *const *pp` | **입력.** 배열이라서 |
| `IASetIndexBuffer(p, ...)` | `ID3D11Buffer *pIndexBuffer` | **입력.** 하나뿐이라 `*` |

별 개수로는 못 가른다. **`const`가 가른다.**

```
const 있음  →  읽기만 함  →  입력  →  Get() (배열이면 GetAddressOf())
const 없음  →  여기에 씀   →  출력  →  GetAddressOf()
```

외우기 쉬운 쪽 — **`Create○○○` 계열의 마지막 인자는 무조건 `GetAddressOf()`.** 예외 없다. 만들어서 어딘가에 넣어줘야 하니 당연하다.

### 3. 변환 결과를 `output.color`에 넣었다

좌표 계산을 VS에서 하는 것까지는 맞았는데 **넣는 자리를 틀렸다.**

```hlsl
float4 position : SV_Position;   // 화면 어디에. 래스터라이저가 이걸 본다
float4 color    : COLOR;         // 무슨 색으로. PS로 보간돼 간다
```

같이 나온 실수 — `float4(float2, float2, 0, 0)`으로 **6칸을 넣었다.** `float4`는 4칸이다. HLSL 생성자가 벡터를 펼쳐 넣는다는 걸 알고 나서 오히려 과하게 쓴 경우.

### 4. 셰이더를 고쳤는데 화면이 안 변했다 — **코드 문제가 아니었다**

오늘 가장 값진 사건이다. 원인이 소스가 아니라 **빌드 파이프라인**이었다.

```
소스        shaders/Sprite.vs.hlsl                 18:55   output.color = input.color;
출력 폴더   build/x64/Debug/shaders/Sprite.vs.hlsl  17:54   float4(spriteSize / screenSize, ...)
                                                    ↑ 한 시간 전 것
```

셰이더는 exe에 박히지 않는다. **런타임에 `D3DCompileFromFile`이 exe 옆 폴더에서 읽는다.** 소스 폴더에서 거기로 복사하는 것은 빌드 후 이벤트(`xcopy`)다.

**함정은 `.hlsl`이 `<None>` 항목이라는 것.**

```xml
<None Include="shaders\Sprite.vs.hlsl" />
```

`<None>`은 빌드 입력이 아니다. 그래서 `.hlsl`만 고치면 Visual Studio가 **"최신 상태"로 판단해 빌드 자체를 건너뛴다.** 빌드를 건너뛰면 빌드 후 이벤트도 안 돈다. `F5`를 눌러도 마찬가지다.

**대처 둘**

1. 셰이더만 고쳤으면 **재빌드(Rebuild)**를 누른다
2. 또는 파일만 출력 폴더로 직접 복사하고 exe를 다시 실행한다 — 셰이더가 런타임에 읽히니 **재컴파일이 아예 필요 없다.** 이게 이 구조의 진짜 장점이고, 셰이더를 자주 만질 4단계 이후로 이쪽이 빠르다

**그리고 디버깅 순서에 0번이 생겼다.**

> **"고쳤는데 안 변한다"의 첫 번째 의심은 코드가 아니다.
> 내가 고친 파일을 프로그램이 진짜 읽고 있는가다.**

교재 00장의 디버깅 순서 1번(출력 창)보다 앞이다. 이걸 몰랐으면 셰이더 문법을 한참 들여다봤을 것이다.

## 오늘의 수확 — 무엇이 잡히고 무엇이 안 잡히는가

어제 예고한 표가 하루 만에 다 찼다. **이게 오늘의 핵심이다.**

| 실수 | 언제 잡히나 |
|---|---|
| `Get()` ↔ `GetAddressOf()` | **컴파일 에러** — 타입이 다르니까 |
| `float4`에 6칸 | **컴파일 에러** — 셰이더 컴파일러가 잡는다 |
| 상수 버퍼 `ByteWidth = 24` | **`CreateBuffer` 실패** — 규칙 A는 검증한다 |
| 인덱스 버퍼 미생성 | **디버그 레이어 경고** — 화면은 비지만 이유는 알려준다 |
| `BindFlags`를 INDEX로 바꿈 | **안 잡힘** |
| `D3D10_` 접두사 | **안 잡힘** — 값이 같아서 통과 |
| 상수 버퍼 안쪽 배치 어긋남 (규칙 B) | **안 잡힘** — 값만 틀리게 나온다 |
| 셰이더 파일이 옛날 것 | **안 잡힘** — 모든 게 정상으로 보인다 |

경계가 명확하다.

**C++ 타입 시스템이 지켜주는 범위와 D3D 런타임이 지켜주는 범위가 다르고, 그 둘 바깥이 제일 넓다.**

- **C++ 안**에서는 타입이 잡아준다
- **API 경계**에서는 DESC의 구조(크기, 플래그 조합)까지만 검증한다
- **GPU 쪽으로 넘어가면** — 바이트 배치, 오프셋, 파일 내용 — 아무도 안 잡는다

어제 입력 레이아웃에서 얻은 한 줄이 오늘 상수 버퍼에서 똑같이 나왔다.

> **GPU 파이프라인에는 타입이 없다. 바이트와 해석 규칙만 있다.**

## 질문과 답

오늘 오간 것 중 남길 만한 것.

### `{0,1,2, 0,2,3}`을 `{0,1,2, 2,3,0}`으로 바꿔도 왜 같은가

**순환 이동은 와인딩을 보존한다.** `0→2→3`과 `2→3→0`은 같은 고리를 시작점만 바꿔 도는 것이다.

정점 3개를 나열하는 6가지가 와인딩 기준으로 두 편으로 갈린다.

| 앞면 (시계) | 뒷면 (반시계) |
|---|---|
| `0,2,3` / `2,3,0` / `3,0,2` | `0,3,2` / `3,2,0` / `2,0,3` |

**왼쪽 셋은 서로 회전이다.** 두 편을 오가려면 **아무 둘을 맞바꿔야** 한다. 부호와 같다 — 순환은 부호를 안 바꾸고, 교환은 한 번마다 뒤집는다. GPU도 세 점으로 만든 부호 있는 면적의 **부호**만 본다.

> **그래서 "정점 순서가 시계 방향이어야 한다"는 부정확하다.** 정확히는 **순환 방향**이 시계여야 한다. 어디서 시작하든 상관없다.

**그림은 같아도 성능은 다를 수 있다.** 포스트-트랜스폼 정점 캐시는 FIFO(16~32칸)라, 인덱스가 재등장할 때 아직 캐시에 남아 있어야 적중한다. 사각형 하나에선 차이가 없지만 정점 5만 개짜리 메시에서는 적중률이 갈린다. 그래서 **정점 캐시 최적화**(Forsyth 알고리즘, `meshoptimizer`)라는 게 따로 있다 — 그림을 안 바꾸고 인덱스 순서만 재배열한다.

**"그림에는 영향 없지만 성능에는 영향 있다"** — 이 프로젝트가 통째로 이 얘기다.

### 사각형에 대각선 자국이 왜 안 보이나

두 삼각형이 **변 0–2를 공유한다.** 그 변 위의 픽셀을 칠할 때 양쪽 다 재료가 **정점 0의 색과 정점 2의 색뿐**이라 결과가 정확히 일치한다.

**다만 "자국이 없다"와 "매끄럽다"는 다르다.** 색은 이어지지만 **기울기는 대각선에서 꺾인다.** 래스터라이저는 사각형을 모르고 삼각형 안에서만 보간하므로, 사각형 전체를 훑는 그라데이션이 아니라 **삼각형 두 장의 그라데이션이 대각선에서 만난 것**이다.

보이게 하려면 대각선 양 끝(0, 2)을 같은 색, 나머지 둘(1, 3)을 반대로 주면 된다.

> 실무에서는 — 지형 같은 큰 평면에 라이팅을 정점에 구우면 격자 대각선이 드러난다. 3D에서는 사각형을 `0-2`로 자르냐 `1-3`으로 자르냐에 따라 **실루엣 자체가 달라진다.**

### 모든 것이 삼각형인가

그렇다. GPU가 면을 채우는 방법은 삼각형뿐이다. 사각형을 기본 단위로 못 삼는 이유가 셋이다.

| | 삼각형 | 사각형 |
|---|---|---|
| **평면성** | 점 3개는 반드시 한 평면 | 비틀릴 수 있다 → 면의 정의가 애매 |
| **볼록성** | 항상 볼록 | 오목할 수 있다(ㄱ자) → 안/밖 판정이 복잡 |
| **보간** | 무게중심 좌표로 **유일하게** 정해짐 | 어느 대각선으로 자르냐에 따라 달라짐 |

**세 번째가 오늘 직접 본 것이다.** 인덱스를 `{0,1,2, 0,2,3}`으로 쓴 게 "0-2로 자르겠다"를 우리가 고른 것이고, GPU는 사각형을 모르니 그 선택을 우리에게 떠넘겼다.

**즉 삼각형은 정의가 애매해질 수 없는 최소 단위다.**

이 프로젝트에 바로 붙는 것 — **스프라이트 1개 = 삼각형 2개.** 7단계에서 스프라이트 10,000개는 **삼각형 20,000개**이고, 계측할 때 이 단위로 말해야 한다.

### HLSL의 `spriteSize`가 어떻게 C++의 `sizeX`를 받나

**이름이 연결하는 게 아니다. 바이트 위치가 연결한다.**

```
바이트   0     4     8     12    16    20    24    28    32
        ├─────┼─────┼─────┼─────┼─────┼─────┼─────┼─────┤
C++     screen screen  posX  posY  sizeX sizeY  pad   pad
        Width  Height
HLSL    └─ screenSize ─┘└─ spritePos ─┘└─ spriteSize ┘└─ padding ─┘
```

`memcpy`는 32바이트를 통째로 복사한다. **필드 이름은 복사되지 않는다** — 컴파일된 코드에 이름 같은 건 없다. `sizeX`가 16~19번지에 앉고 `spriteSize.x`가 16~19번지를 읽으니 통하는 것이다.

**증명** — HLSL 쪽 이름을 `aaa, bbb, ccc, ddd`로 바꿔도 똑같이 돈다. 반대로 **순서만 바꾸면** 이름이 그대로여도 값이 뒤바뀐다.

**입력 레이아웃과는 다르다는 것이 중요하다.**

| | 짝을 맞추는 법 | 이름 틀리면 |
|---|---|---|
| 입력 레이아웃 | **시맨틱 이름** + 오프셋 | `CreateInputLayout` **실패** |
| 상수 버퍼 | **슬롯 번호(`b0`) + 오프셋만** | 아무 일도 안 일어남 |

정점 쪽은 `CreateInputLayout`에 셰이더 바이트코드를 같이 넘겨 런타임이 이름을 대조한다. **상수 버퍼에는 그런 대조 단계가 아예 없다.** 그래서 규칙 B(16바이트 정렬)가 위험한 것이다 — 대조해주는 사람이 없다.

### `cbuffer` 선언이 버퍼를 만드는 건가

아니다. **HLSL은 아무것도 안 만든다.** `cbuffer`는 "b0에 꽂혀 있을 32바이트를 이렇게 읽겠다"는 **해석 규칙**이다.

| 하는 일 | 어디서 | 실체 |
|---|---|---|
| 그릇을 만든다 | C++ `CreateBuffer` | 진짜 GPU 메모리 |
| 내용을 채운다 | C++ `Map`/`memcpy` | 값 |
| 꽂는다 | C++ `VSSetConstantBuffers(0, ...)` | b0 슬롯에 연결 |
| 읽는 법을 정한다 | HLSL `cbuffer : register(b0)` | **메모리 없음** |

C++ 함수 선언과 같다. `void f(int x)`는 `x`를 만들지 않는다. 부르는 쪽이 준다.

**b0에 아무것도 안 꽂아도 `cbuffer` 선언은 그대로 있고, 그때 읽으면 0이 나온다.** HLSL이 버퍼를 만드는 거였다면 0이 나올 리가 없다.

> 슬롯은 `b0`~`b13` 14칸이다. 실무에서는 **갱신 빈도로 나눈다** — 카메라 행렬처럼 안 바뀌는 건 `b0`에 한 번, 오브젝트마다 바뀌는 건 `b1`에. 섞어두면 안 바뀐 것까지 매번 다시 올려야 한다. 6단계 드로우 콜 비용과 직결된다.
> 접두사도 종류별로 다르다. `b`=buffer, `t`=texture, `s`=sampler. **4단계에서 `t0`, `s0`가 나온다.**

### 왜 값을 색으로 출력해서 확인하나

**셰이더는 디버거로 못 본다.** 중단점도, 변수 감시도, `printf`도 없다. 게다가 수만 개가 병렬로 돌아서 "그중 어느 실행의 값"인지부터 애매하다.

셰이더가 바깥으로 내보낼 수 있는 건 **픽셀 색 하나뿐**이다. 그래서 알고 싶은 값을 색 자리에 밀어넣고 화면을 본다. **화면이 출력 창을 대신한다.**

임시방편이 아니라 정식 기법이고 이름도 있다 — **false color / debug visualization.** 언리얼의 View Mode(Base Color, Normal 보기)가 정확히 이거다.

오늘 실제로 쓴 것.

```hlsl
output.color = float4(spriteSize / screenSize, 0.0f, 1.0f);
```

`spriteSize=(1280, 0)`, `screenSize=(1280, 720)`이니 `(1.0, 0.0)` → **순수 빨강**이 나와야 한다. 나왔다.

**색 하나로 32바이트 전체가 검증된다.**

| 실제로 읽힌 게 | 계산 | 화면 |
|---|---|---|
| `sizeX` (1280) ← 맞음 | 1280/1280 = 1.0 | **선명한 빨강** |
| `posY` (360) | 360/1280 = 0.28 | 어두운 빨강 |
| `padding` (0) | 0/1280 = 0 | 검정 |

오프셋 0과 16이 둘 다 맞으면 그 사이의 8이 어긋날 방법이 없다.

**부수적으로 상수 버퍼의 정의도 눈으로 봤다** — 그라데이션이 사라지고 균일한 단색이 됐다. VS가 네 번 도는데 네 번 다 같은 값을 읽으니까. 교재 표의 "정점마다 다른 값 / 모든 정점이 같이 쓰는 값"이 그대로 화면에 나온 것.

**앞으로 쓸 때 규칙 셋**

1. **0~1로 정규화한다.** 1280을 그냥 넣으면 클램프돼 무조건 흰색
2. **음수는 안 보인다.** `값 * 0.5 + 0.5`로 옮기거나 `abs()`
3. **한 번에 한 값만.** 세 개를 RGB에 밀어넣으면 역산하다 잘못 읽는다

### 상수 버퍼로 옮기는 게 정점 버퍼를 고치는 것과 같은 일인가

결과는 같고 **비용 구조가 다르다.** 그리고 "정점 버퍼가 비싸서"는 반만 맞다 — 정점 버퍼 자체가 아니라 **매 프레임 다시 쓰는 것**이 비싸다.

| | A. 정점 버퍼 갱신 | B. 상수 버퍼 갱신 |
|---|---|---|
| 매 프레임 쓰는 양 | 4정점 × 24바이트 = 96바이트 | **32바이트** |
| 버퍼 `Usage` | `DYNAMIC`이어야 함 (느린 메모리) | 정점은 `IMMUTABLE` 유지 |
| 정점이 커지면 | UV·법선 붙으면 160바이트+ | **여전히 32바이트** |

**하지만 진짜 이유는 따로 있다.**

정점에 위치를 박으면 **스프라이트마다 정점 버퍼가 따로 필요해진다.** 10,000개면 10,000개분.

B는 정점 버퍼가 **"0~1 단위 사각형" 하나뿐**이고 전부가 그걸 공유한다.

```
정점 버퍼   [단위 사각형 4정점]           ← 하나. 아무도 안 건드림
위치 데이터 [스프라이트0][1][2]...[9999]  ← 이것만 다르다
```

**7단계 인스턴싱이 정확히 이 구조다.** 오늘 정점을 `0~1`로 바꾼 것이 그 예행연습이었다. 7단계에서는 상수 버퍼 대신 **인스턴스 버퍼**로 10,000개를 한 번에 넘긴다. 정점 버퍼는 그대로 둔 채로.

## 확인 문제 — 답하고 보완한 것

하루를 마치고 10문제를 풀었다. 결과에서 **경계가 뚜렷하게 나왔다.**

> **말로 설명하라는 문제는 되는데, 숫자를 넣거나 새 상황에 규칙을 대보라는 문제에서 무너진다.**

개념(1·2·3·7·9)은 대체로 맞고 적용(5·6·8·10)이 틀렸다.
어제 일지 첫 줄에 적은 **"읽어서 아는 것과 결과를 미리 맞힐 수 있는 것은 다르다"**가 그대로 재현됐다.
오늘 하루 새 개념을 다섯 개 얹었으니, 아직 굳지 않은 것이 정상이다.

### 맞은 것

| # | 물은 것 | 핵심 |
|---|---|---|
| 2 | `IMMUTABLE` / `DYNAMIC` 선택 기준 | 정점·인덱스는 전자, 상수는 후자 |
| 3 | `cbuffer`가 메모리를 만드는가 | 아니다. `b0`를 어떻게 읽을지의 규칙일 뿐 |
| 7 | 인덱스를 `{3,2,0}`으로 바꾸면 | 순환이 아니라 뒤집힘 → 그 삼각형만 사라진다 |

**1번은 절반이었다.** "인덱스 버퍼 없이 정점 버퍼만으로도 그려진다"까지는 맞았는데,
둘 다 필요한 이유를 **"대각선 방향을 정하려고"**라고 답했다. 틀렸다 —
인덱스 없이 정점 6개로 그려도 대각선은 정해진다. 인덱스 버퍼의 일은 **정점 재사용**이고,
그중 큰 쪽은 메모리가 아니라 **VS 실행 결과의 재사용**이다.

**4번도 절반.** "같은 레지스터에 넣었으니 값이 통한다"고 답했는데, 레지스터는
*어느 버퍼인지*까지만 정한다. 그 안에서 어느 값인지는 **바이트 오프셋**이 정한다.

### 풀다가 나온 질문 둘

**Q. 상수 버퍼 값이 매 프레임 똑같은데 이걸 "변한다"고 해야 하나?**

기준은 **"값이 변하느냐"가 아니라 "CPU가 쓸 수 있어야 하느냐"**다.
`IMMUTABLE`은 만들 때 넣고 영원히 못 바꾼다 — `Map`이 아예 실패한다.

그리고 지금도 실제로 변하는 값이 하나 있다. **창 크기를 바꾸면 `screenSize`가 바뀐다.**
`Resize()`가 `m_width`/`m_height`를 갱신하기 때문이다. 창을 늘리면 사각형은 200×200을
유지한 채 화면에서의 상대 위치가 바뀐다. 그게 `DYNAMIC`이 필요한 증거다.

**Q. `cbuffer`를 `register(b1)`로 바꾸면 아까 만든 버퍼를 못 읽나?**

못 읽는다. `b1`은 비어 있고, **빈 슬롯을 읽으면 0이 온다.**
`screenSize`가 `(0,0)`이 되어 0으로 나누고, `NaN`이 된 좌표는 래스터라이저가 통째로 버린다.
**화면에서 사각형이 사라진다.**

### 틀린 것 ① — 좌표 변환에서 두 군데

정점 2번(우하, 비율 `(1,1)`)의 NDC를 물었는데 `(0.5, 0.5)`라고 답했다.

**비율을 안 더했다.** `spritePos`만 쓴 것은 정점 0번(좌상)이다.
그리고 **x와 y 공식을 서로 바꿔 썼다.**

```
screenPos = spritePos + input.position * spriteSize
          = (480, 810) + (1,1) * (300, 150) = (780, 960)

ndc = (780/1920, 960/1080) = (0.40625, 0.8889)

x = 0.40625 * 2 - 1 = -0.1875     ← x는 *2-1
y = 1 - 0.8889 * 2  = -0.7778     ← y는 1-*2
```

> **공식이 헷갈리면 꼭짓점으로 검산한다.**
> 화면 `(0,0)`은 NDC `(-1,+1)`이어야 하고 `(1920,1080)`은 `(+1,-1)`이어야 한다.
> 30초면 어느 쪽이 어느 공식인지 확정된다.

### 틀린 것 ② — 16바이트 정렬. 오늘 경고한 함정에 그대로 걸렸다

```hlsl
cbuffer Test { float2 a; float3 b; float c; float4 d; };
```

이걸 두고 **"쓸 거 다 쓰고 마지막을 패딩으로 채운다"**고 답했다.
**이 배치에서는 그게 안 통한다.** 오늘 아침에 적어둔 그대로다 — 필요한 패딩이 끝이 아니라 중간이다.

```
a (float2,  8)   0 ~  7    그대로
b (float3, 12)   8~19에 놓고 싶지만 16을 넘는다 → 16 ~ 27로 밀린다
c (float,   4)  28 ~ 31
d (float4, 16)  32 ~ 47

ByteWidth = 48
```

```cpp
struct Test
{
    float a[2];        //  0 ~  7
    float pad0[2];     //  8 ~ 15   ← 중간 패딩. 없으면 b가 8번지에 앉아 어긋난다
    float b[3];        // 16 ~ 27
    float c;           // 28 ~ 31
    float d[4];        // 32 ~ 47
};
```

**끝에는 패딩이 필요 없다.** 48이 이미 16의 배수라 규칙 A는 저절로 충족됐고,
손봐야 했던 것은 규칙 B였다. **두 규칙이 서로 다른 곳을 고치게 만든다는 것이 요점이다.**

### 틀린 것 ③ — 데이터 양보다 드로우 콜

스프라이트 1,000개를 그릴 때 올려보내는 바이트를 물었다.

```
(나) 정점 버퍼 갱신   4정점 × 24바이트 × 1,000 = 96,000
(가) 상수 버퍼 갱신   32바이트 × 1,000        = 32,000
```

`24 × 1000`이라고 답했다. **사각형 하나에 정점이 4개**인 것을 빠뜨렸다.

**그런데 여기서 더 중요한 것을 알게 됐다 — 6·7단계의 병목은 이 바이트 수가 아니다.**

```
지금 구조    상수 버퍼 갱신 1,000번 + DrawIndexed 1,000번
인스턴싱     인스턴스 버퍼 갱신 1번   + DrawIndexedInstanced 1번
```

데이터 양은 비슷한데 **드로우 콜이 1,000배 차이난다.** 8단계에서 잴 것이 정확히 이거다.

### 틀린 것 ④ — 무엇이 잡히고 무엇이 안 잡히는가

다섯 개를 분류하는 문제. 이게 오늘의 핵심이었는데 **두 개를 틀렸다.**

| | 실수 | 내 답 | 실제 |
|---|---|---|---|
| a | `uint32_t` 인덱스를 `R16_UINT`로 읽음 | ③ | **③** 인덱스가 `{0,0,1}{0,2,0}`으로 읽혀 퇴화 삼각형이 된다 |
| b | `cbuffer` 멤버 **순서만** 바꿈 | ③ (이유 틀림) | **③** "문제 없음"이 아니라 **값이 통째로 뒤바뀐다** |
| c | `VSSetConstantBuffers(1, ...)` | ① | **③** 완벽하게 합법인 호출이다 |
| d | `float4(ndc, 0.0f)` — 3칸 | ① | **①** |
| e | `ByteWidth = 40` | ③ | **②** `40 % 16 = 8` → `CreateBuffer` 실패 |

**b의 실제 증상** — `spriteSize` 자리에서 `posX, posY`를, `spritePos` 자리에서 `sizeX, sizeY`를
읽는다. 사각형이 `(200,200)` 위치에 `100×50` 크기로 뜬다. 아무 경고 없이.

**c와 e를 반대로 짚은 것이 이 표의 요지를 놓친 지점이다.**

- `c`는 **슬롯 번호가 그냥 `UINT`**라 컴파일러가 막을 이유가 없다.
  어제 `Draw(2, 0)`이 합법이라 조용했던 것과 같은 부류다
- `e`는 **규칙 A가 검증되는 항목**이라 만들 때 시끄럽게 죽는다.
  "NDC 값만 이상해진다"는 규칙 B를 어겼을 때의 증상이지 A가 아니다

### 다시 볼 것 둘

말로 하는 것은 되니 개념은 잡혔다. **적용이 안 되는 두 곳만 다시 한다.**

1. **16바이트 정렬** — 4단계에서 텍스처 상수를 추가할 때 그대로 당할 자리다
2. **좌표 변환** — 셰이더 코드를 손으로 따라가며 한 번 더

## 다음 (4단계)

텍스처와 샘플러. 스프라이트에 실제 그림을 붙인다.

오늘 것이 세 개 이어진다.

- **UV도 `SV_` 없는 값이라 보간을 탄다** — 색이 간 길로 UV가 간다
- **UV는 `0~1`이고 y가 아래로 +다** — 오늘 정점을 `0~1` 단위 사각형으로 바꿔둔 것과 방향이 같아서, UV를 따로 안 넣고 `input.position`을 그대로 UV로 쓸 수 있다
- **`t0`, `s0` 슬롯** — `b0`와 같은 구조. 접두사만 다르다

그리고 오늘 얻은 디버깅 순서 0번을 바로 쓰게 된다. 셰이더를 자주 고칠 단계라 **재빌드 안 하고 파일만 복사하는 방식**을 시험해볼 자리다.
