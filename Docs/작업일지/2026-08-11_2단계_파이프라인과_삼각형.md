# 2단계 — 렌더링 파이프라인과 삼각형

> 상태: 완료 · 갱신 2026-08-11 · 관련: [작업일지 목차](../_목차.md), [기초 — 창과 D3D11의 등장인물](../개념/00_기초_창과_D3D11의_등장인물.md), [7일 커리큘럼](../7일_커리큘럼.md)
> 무엇: 정점 3개가 화면의 픽셀이 되기까지. 셰이더 컴파일, 입력 레이아웃, 정점 버퍼, 드로우 콜을 처음 붙인 기록.

## 결과

화면 가운데 삼각형이 뜬다. 꼭짓점이 각각 빨강·초록·파랑이고, 안쪽은 세 색이 섞여 있다.

**정점은 3개인데 색은 수십만 픽셀에 걸쳐 부드럽게 변한다.**
이걸 우리가 계산한 적이 없다. 래스터라이저가 자동으로 해준 것이다. → 아래 "보간" 참고

---

## 왜 어렵게 느껴졌나

새 개념이 다섯 개 한꺼번에 나오기 때문이다. **각각은 한 문장이다.**

| | 한 문장 |
|---|---|
| 셰이더 | GPU에서 도는 아주 작은 프로그램 |
| 셰이더 컴파일 | `.hlsl` 텍스트를 GPU가 알아듣는 바이트코드로 번역 |
| 정점 버퍼 | 정점 데이터를 GPU 메모리에 올려둔 것 |
| 입력 레이아웃 | 그 바이트 뭉치를 어떻게 해석할지 알려주는 규칙 |
| 드로우 콜 | "그려" 한마디 |

어려운 게 아니라 **양이 많은 것**이다. 하나씩 보면 다 짧다.

---

## 전체 흐름

```
한 번만 (Initialize)                        매 프레임 (Render)
──────────────────────                     ──────────────────
1. HLSL 컴파일 -> 바이트코드                 IASetInputLayout
2. 바이트코드 -> 셰이더 객체                  IASetVertexBuffers
3. 입력 레이아웃 만들기                       IASetPrimitiveTopology
4. 정점 버퍼 만들기                          VSSetShader
                                            PSSetShader
                                            Draw(3, 0)   <- "그려"
```

**만드는 건 한 번, 꽂는 건 매 프레임.** 이 구분이 D3D11의 기본 리듬이다.

---

## 조각별로

### 1. 셰이더는 GPU에서 도는 프로그램이다

C++는 CPU에서 돈다. 셰이더는 GPU에서 돈다. 언어가 HLSL로 다를 뿐 프로그램이다.

| | 언제 도나 | 몇 번 |
|---|---|---|
| 정점 셰이더 (VS) | 정점 하나당 | 삼각형 하나 = **3번** |
| 픽셀 셰이더 (PS) | 삼각형이 덮은 픽셀 하나당 | 화면 반 = **수십만 번** |

**이 횟수 차이가 성능의 핵심이다.** 같은 계산이라도 VS에 두느냐 PS에 두느냐로 비용이 만 배 난다.
"무거운 계산은 최대한 정점 단계로 올린다"가 여기서 나온다.

### 2. 컴파일이 실행 중에 일어난다

C++는 빌드할 때 미리 기계어가 된다. 셰이더는 다르다.
`.hlsl` 파일을 텍스트 그대로 두었다가, **프로그램이 실행될 때** `D3DCompileFromFile`이 번역한다.

```cpp
CompileShaderFromFile(L"shaders\\Triangle.vs.hlsl", "main", "vs_5_0", vsBlob);
//                                                    ↑        ↑
//                                            시작 함수 이름   셰이더 모델 버전
```

GPU마다 명령어 집합이 달라서, 실행되는 그 기계에서 번역하는 편이 안전하기 때문이다.
(미리 `fxc.exe`로 번역해 `.cso`로 만들어 두는 방법도 있다. 시작 시간이 줄지만 지금은 불필요)

**컴파일 오류 메시지를 반드시 띄우게 해야 한다.** HRESULT만 보면 아무것도 알 수 없고,
"몇 번째 줄 무슨 문법 오류"는 `errorBlob` 안에 문장으로 들어 있다.
이걸 안 보여주면 셰이더 디버깅이 불가능하다.

### 3. 입력 레이아웃 — 바이트 해석 규칙

GPU에게 정점 버퍼는 **그냥 바이트 뭉치**다. 어디까지가 위치이고 어디부터 색인지 모른다.

```
Vertex 구조체가 메모리에 깔린 모습

바이트  0   4   8   12  16  20  24
       [x] [y] [r] [g] [b] [a]
       └POSITION┘ └───COLOR───┘
        8바이트      16바이트
```

이걸 그대로 적은 것이 입력 레이아웃이다.

```cpp
{ "POSITION", 0, DXGI_FORMAT_R32G32_FLOAT,       0, 0, D3D11_INPUT_PER_VERTEX_DATA, 0 },
{ "COLOR",    0, DXGI_FORMAT_R32G32B32A32_FLOAT, 0, 8, D3D11_INPUT_PER_VERTEX_DATA, 0 },
//   ↑                    ↑                          ↑
// 시맨틱 이름       float 몇 개짜리인지        시작 오프셋(바이트)
```

**시맨틱 이름(`"POSITION"`, `"COLOR"`)은 HLSL의 `: POSITION`, `: COLOR`와 글자까지 같아야 한다.**
이게 C++와 셰이더를 잇는 유일한 끈이다.

그래서 셋이 항상 함께 맞아야 한다 — **C++ `Vertex` 구조체 ↔ 입력 레이아웃 ↔ HLSL `VSInput`.**
하나만 고치면 반드시 깨진다. 앞으로 정점에 뭔가 추가할 때마다 세 군데를 같이 고쳐야 한다.

`CreateInputLayout`에 정점 셰이더 바이트코드를 같이 넘기는 이유가 여기 있다.
런타임이 그 자리에서 "이 레이아웃이 저 셰이더 입력과 맞는가"를 검증한다. 오타 내면 여기서 실패한다.

### 4. 정점 버퍼 — GPU 메모리에 올려두기

```cpp
desc.Usage     = D3D11_USAGE_IMMUTABLE;   // 만든 뒤 절대 안 바뀜
desc.BindFlags = D3D11_BIND_VERTEX_BUFFER;
```

`IMMUTABLE`은 "한 번 만들면 끝"이라는 약속이다. 그 대가로 GPU가 가장 빠른 메모리에 둘 수 있다.
매 프레임 내용이 바뀌어야 하면 `DYNAMIC` + `CPU_ACCESS_WRITE`를 쓴다. (6일차 배칭에서 그렇게 한다)

**좌표는 NDC다.** 화면 중앙이 (0,0), 위가 +y, 범위는 -1 ~ +1.
픽셀 좌표가 아니라서 창 크기가 바뀌어도 삼각형이 같은 비율로 늘어난다.

**정점 순서는 시계 방향이어야 한다.** D3D는 기본적으로 시계 방향을 앞면으로 보고,
뒷면은 아예 그리지 않고 버린다(백페이스 컬링). 3D에서 안 보이는 뒷면 계산을 건너뛰려는 최적화인데,
2D에서도 그대로 적용된다. 반시계로 적으면 삼각형이 그냥 사라진다.

### 5. Draw는 "그려" 한마디다

```cpp
m_context->Draw(3, 0);   // 정점 3개를, 0번부터
```

**무엇을, 어디에, 어떻게가 하나도 안 들어간다.** 그래서 그 전에 전부 꽂아둬야 한다.

```cpp
m_context->IASetInputLayout(...);        // 바이트 해석 규칙
m_context->IASetVertexBuffers(...);      // 어느 버퍼에서 읽을지
m_context->IASetPrimitiveTopology(...);  // 셋씩 묶어 삼각형으로 볼지
m_context->VSSetShader(...);             // 정점 셰이더
m_context->PSSetShader(...);             // 픽셀 셰이더
```

[기초 노트](../개념/00_기초_창과_D3D11의_등장인물.md)에서 정리한 "상태 의존형"이 바로 이것이다.
어제 `OMSetRenderTargets`를 주석 처리해도 멀쩡했던 이유와 짝을 이룬다.

## 보간 — 정점 3개인데 왜 그라데이션인가

파이프라인에서 VS와 PS 사이에 **래스터라이저(RS)**가 있다. 우리가 코드를 못 쓰는 고정 단계다.

RS가 하는 일은 둘이다.
1. 삼각형을 픽셀 조각으로 쪼갠다
2. **VS가 내놓은 값들을 픽셀 위치에 맞춰 자동으로 섞는다**

두 번째가 보간(interpolation)이다.
꼭짓점 A가 빨강, B가 초록일 때, 그 중간 픽셀은 반반 섞인 색을 받는다.

그래서 PS가 받는 `input.color`는 **정점에 넣은 값이 아니라 이미 섞인 값**이다.
색뿐 아니라 UV 좌표, 법선 등 VS에서 PS로 넘기는 모든 값이 이렇게 자동으로 섞인다.
3일차에 텍스처를 붙일 때 UV가 이 방식으로 넘어간다.

## 셰이더 파일을 어떻게 찾게 했나

`D3DCompileFromFile`은 파일 경로를 받는데, 프로그램의 "현재 작업 폴더"는
어디서 실행했느냐에 따라 달라진다. Visual Studio에서 F5로 돌리면 프로젝트 폴더,
탐색기에서 더블클릭하면 exe 폴더다.

그래서 작업 폴더에 기대지 않고 **exe 위치를 직접 구해서 붙인다.**

```cpp
GetModuleFileNameW(nullptr, exePath, MAX_PATH);   // 실행 중인 exe의 전체 경로
// 마지막 역슬래시까지 남기고 -> "shaders\Triangle.vs.hlsl" 붙이기
```

그리고 빌드가 끝나면 셰이더를 exe 옆으로 복사하도록 후처리를 걸었다.

```xml
<PostBuildEvent>
  <Command>xcopy /Y /D /I "$(ProjectDir)shaders\*.hlsl" "$(OutDir)shaders\"</Command>
</PostBuildEvent>
```

**제출용으로 폴더째 압축해 넘길 때도 이래야 안전하다.** 받는 사람이 어디서 실행하든 돌아간다.

## 손으로 확인할 것

읽는 것보다 깨뜨려 보는 게 빠르다. 각각 왜 그런지 예측하고 나서 돌려볼 것.

1. **정점 순서 뒤집기** — 두 번째와 세 번째 정점을 바꾼다 → **삼각형이 사라진다** (백페이스 컬링)
2. **좌표 바꾸기** — `0.5f`를 `0.9f`로 → NDC 범위 감각을 잡는다
3. **PS를 고정 색으로** — `return float4(1,1,1,1);` → 그라데이션이 사라진다. 보간이 어디서 오는지 확인
4. **시맨틱 오타** — `"COLOR"`를 `"COLOUR"`로 → `CreateInputLayout` 실패. 검증이 실제로 도는 것 확인
5. **HLSL 문법 오류** — 세미콜론 하나 지우기 → 컴파일 오류 메시지 박스 확인
6. **`OMSetRenderTargets` 주석** — **이번엔 진짜로 깨진다.** 어제와 뭐가 달라졌는지가 핵심
